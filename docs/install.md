# Install and operate

Everything lives in one project directory, the git checkout itself (`/zerostress` on a server), and one command, `./zs`, runs it. Every setting is described in [configuration.md](configuration.md).

The reference host: a Vultr VM with nested virtualisation (`/dev/kvm`), Rocky Linux 10, SELinux Enforcing. The public site runs behind Cloudflare (Full strict) with a Let's Encrypt certificate held by Caddy.

## Layout
```
/zerostress/
├── zs                  the one command
├── config/             web.env (holds the model key), supervisor.env: edited by a human; Caddyfile: generated by zs
├── supervisor/ web/ guest/ deploy/ docs/      code (git)
├── bin/                firecracker, zsvm, zsnet, caddy, zerostress-supervisor (owned by root)
├── runtime/            node, go
├── images/             the guest microVM image (read-only in every microVM; replaced only by a rename) and its packages.txt
├── data/               supervisor/ (runs: a run's scratch disk and sockets; results), web/ (reports), geo/, caddy/ (certificates)
├── logs/               web.log, supervisor.log, caddy.log
├── run/                supervisor.sock
└── build/              everything the builds produce
```
Code changes go through git, settings through `./zs config`; the rest is filled by `./zs install` and the services themselves. Outside the directory there is only what the system reads from its own places: units, sudo rules, sysctl, udev, logrotate (from `deploy/files/`, installed by `./zs install`, never edited by hand), SELinux labels and a firewalld zone.

## Commands
```
./zs install [step…]     host | network | runtime | image | supervisor | web | verify; no step means all (sudo)
./zs update              git pull, build and restart the supervisor and the site, verify
./zs start|stop|restart|status
./zs logs [web|supervisor|caddy] [-f]
./zs config [web|supervisor]     edit settings and restart the service
./zs verify [--live]     compare the host with the repository without changing anything
./zs version [set X.Y.Z] the version (see Versions and releases)
./zs release X.Y.Z       tag a release
./zs dev                 the site from your checkout on port 8081, with its own data in build/dev
```
`verify` checks the services, the supervisor's and the site's answers, KVM, the kernel parameter, versions, the owners of `bin/`, SELinux types, the variable names in `config/*.env` (never their values) and that the files from `deploy/files/` match byte for byte. `--live` also runs one real check of `https://example.com/` through the public address and requires it to finish with the verdict *benign* (a failed run has a report too, so a report alone proves nothing); it starts a microVM and counts against the limits.

## A new server
1. A Vultr VM with KVM (Firecracker does not work without `/dev/kvm`; the `host` step checks it first), Rocky Linux 10.
2. `git clone https://github.com/xhero-xandr/zerostress /zerostress && cd /zerostress`
3. Make sure you can log in over SSH with a key as a user besides root (the `host` step closes SSH passwords and root login, but only when such a user has an authorized key). Then `sudo ./zs install host`, then `./zs config web` (the model key), and reboot if the step asks for it (kernel parameter).
4. `sudo ./zs install` (about 15 minutes, most of it the guest image).
5. `./zs verify --live`, then point DNS at the host.

Every step is idempotent, and every download is checked against a pinned checksum in `deploy/versions.env`. To move to another server: the same, plus `config/` and, if you want the reports, `data/` from the old one.

Verified end to end on a clean Vultr instance (8 November 2026): every step through `verify`, then a real check submitted straight to the API (no domain, no Cloudflare there) came back *benign*. The `host` step now also installs `squashfs-tools` (needed to unpack the guest image's base, not part of a minimal Rocky install) and adds the project directory to git's `safe.directory`, so the image manifest's commit is recorded rather than `"unknown"` — both were missing before and had only ever been fixed by hand on the long-lived server.

## Updating
| What changed | Command |
|---|---|
| site, agent, hooks or supervisor code | `./zs update` |
| only the site or only the supervisor | `sudo ./zs install web` / `supervisor` |
| the collector or the guest agent (the image changes) | `sudo ./zs install image supervisor` |
| a version in `deploy/versions.env` | `sudo ./zs install runtime`, then the step that uses it |
| a setting | `./zs config web` |

## The browser extension
The extension (`web/extension/`) is a thin frame: a right-click menu, an icon and a side panel that frames `https://zerostress.space/panel`, where the agent itself lives (a page of the client, updated with the site). Install it from the [Chrome Web Store](https://chromewebstore.google.com/detail/jbfpfekapmgpjjbiigjkhahongcjdlpm), or download the release of the site's version (see [Versions and releases](#versions-and-releases)), or build it: `cd web/client && npm ci --ignore-scripts && npm run build:extension` writes `build/extension`. Load it in Chrome, Edge or Brave: `chrome://extensions` → *Developer mode* → *Load unpacked*. Its id is the Chrome Web Store's own when installed from there, or fixed by the public key in `web/extension/public/manifest.json` otherwise (the store strips that key from the manifest it serves); the web layer lets exactly these two origins frame `/panel` (`EXTENSION_ORIGINS` in `web/server/app.ts`, `frame-ancestors`), and the panel takes links only from one of them. It has no host permission: it never reads a page. It has no `externally_connectable` and no `onMessageExternal`, so another extension cannot message it at all; messages between its side panel and the `/panel` frame check both the sender's origin and its `source`. Known limit, not fixable from the extension's side: a different extension with broad host permissions (`<all_urls>` and `scripting`) can inject a content script into `zerostress.space` wherever it is open, panel or an ordinary tab, same as into any other site; the site's own CSP (`script-src 'self'`, no `unsafe-inline`/`unsafe-eval`) is what limits that, not anything the extension does.

## Versions and releases
One version for the whole project (the site, the supervisor, the guest's collector, the browser extension), kept in
`VERSION`; `./zs version` shows it, this checkout's build and the running supervisor's. A build between two releases is
`X.Y.Z+N.gHASH` (N commits after release X.Y.Z), and one on the way to a version not yet tagged is `X.Y.Z-dev+N.gHASH`: the site shows it in its footer, the supervisor in `/v1/health`, and
`./zs verify` checks that the running supervisor belongs to the release in `VERSION`.

The project stays below 1.0.0 until it is stable: fixes raise the last number (0.9.1), new capabilities the middle one
(0.10.0). Each release is an annotated tag `vX.Y.Z` on `main`, and its notes are its section of
[CHANGELOG.md](../CHANGELOG.md). Versions 0.1.0 to 0.8.0 were tagged afterwards on the commits of their milestones.

1. `./zs version set X.Y.Z` writes the version into `VERSION`, the extension's manifest and every `package.json` and lock
   file, and turns the entries under `## [Unreleased]` in `CHANGELOG.md` into a dated section. Review it and commit.
2. `./zs release X.Y.Z` checks that every place agrees, that the tree is clean and you are on `main`, then makes the tag.
3. `git push origin main && git push origin vX.Y.Z`: the release workflow checks the same again, checks that the tag is
   on `main`, runs the client's tests, builds the extension and publishes the GitHub release with
   `zerostress-extension-X.Y.Z.zip` and its SHA-256.

The site links to the extension of its own release
(`https://github.com/xhero-xandr/zerostress/releases/download/vX.Y.Z/zerostress-extension-X.Y.Z.zip`), never to
"latest". The agent inside the extension is the page `/panel` of the site, so it changes with every deploy; the
extension needs replacing only when its own version does. `deploy/test/release-check.sh` (in CI) makes sure each of
these checks refuses what it should.

## Development
- The site runs straight from the checkout: a change in `web/` goes live when the service restarts (`./zs update` or `./zs restart`). To try a change first: `./zs dev`.
- On your own machine: `git clone`, `cp config/web.env.example config/web.env` (the key is optional), `./zs dev`. Without KVM no real link checks run (there is no supervisor), but the interface, the report and the chat work.

## Tests
Without KVM (these also run in CI): `npm test` and `npm run typecheck` in `web/` and `web/client/` (the client's typecheck covers the extension's sources), `node --test extension/test/*.mjs` and `npm run build:extension`, `npm run e2e` in `web/client/` (a browser check of the CSP, Chromium as a regular user), `npm test` in `guest/collector/`, `supervisor/build.sh` and `guest/agent/build.sh` (tests with `-race`), `deploy/test/mutate-artifacts.sh` (29 mutations of the Go code: artifact hand-over, approvals bound to the command hash and their expiry, which commands are risky, command size and fields, slot quarantine, session slots, the hard timeout, request and guest line limits, run ids; about 40 seconds). Mutation testing of the web layer: `npm run mutate` in `web/` (about 40 minutes).

On real microVMs (on the server only, as `root`; everything they create they clean up; they target `/zerostress`):
```
deploy/test/image-smoke.sh            image: overlay, boot, guest agent over vsock, Chromium, network
deploy/test/image-net-isolation.sh    network isolation between two guests
deploy/test/image-collector.sh        the real collector in a microVM against example.com
deploy/test/image-session.sh          guest agent sessions over real vsock
deploy/test/supervisor-suite.sh       the next three in one run: lays the stub collector over the image, sets SUP_CONCURRENCY=2 and SUP_SESSION_SLOTS=1 temporarily, and always puts everything back (about 8 minutes; the site answers with test results meanwhile)
deploy/test/supervisor-e2e.sh         the supervisor service with real microVMs (47 checks; image with a stub collector)
deploy/test/supervisor-sessions-e2e.sh  commands, approvals, idle time, slots (about 3 minutes)
deploy/test/supervisor-timeouts.sh    time limits (about 2 minutes; changes the unit temporarily)
deploy/test/collector-e2e.sh          the real collector behind the supervisor (swaps the image for the test, by a rename)
deploy/test/agent-e2e.sh              the whole agent: supervisor, microVM, collector, hooks, the real model
deploy/test/containment-e2e.sh        isolation from inside a microVM: cloud metadata, the host, internal networks, its disks; memory, CPU, a full disk
deploy/test/zsnet-netns.sh            the real zsnet in throwaway network namespaces, real traffic: mail ports, the new-connection rate, the table rebuilt on a new ruleset (the host's network is untouched)
deploy/test/zsvm-helper.sh            zsvm rejects everything malformed
deploy/test/zsvm-isolation.sh         what an escape into Firecracker could reach: the supervisor, other VMs, the project
deploy/test/image-readonly.sh         the image is read-only, the guest boots over its own scratch disk (next to live checks)
deploy/test/zsvm-probe.sh             the microVM unit: cgroup, signals, cleanup (stop the supervisor first)
deploy/test/unit-compat.sh LABEL PROP...  compatibility of unit properties with SELinux
deploy/test/bench-concurrency.mjs     memory, CPU and timings at 1 to 4 microVMs at once (changes the unit temporarily)
```
Measurements through the live site (they count against its limits): `node web/tools/quality.mjs` (live phishing from OpenPhish and large sites known for bot walls, through the whole pipeline) and `node web/tools/panel-check.mjs [link] [allow|deny]` (one deep check through the browser extension, with the approval answered), both as the owner of the checkout. `./zs install` prepares what `panel-check.mjs` needs: Chromium's system libraries (`10-host.sh`), Playwright's Chromium in the code owner's home and the extension build (`60-web.sh`); `./zs verify` checks them. The host step also gives the administrators (human members of the group `wheel` or `sudo`, or exactly `ADMIN_USER`) access to the checkout by ACL and git's `safe.directory`, sets the repository's author (`GIT_NAME`, `GIT_EMAIL`), and closes SSH passwords and root login, but only when a user besides root has an authorized key, so it cannot lock the owner out.
The image tests need the guest agent (`guest/agent/build.sh`). An image with the stub collector is built explicitly: `COLLECTOR_ENTRY=deploy/test/stub-collector.mjs guest/image/build.sh` (the real collector is the default).

If a test was interrupted, these should all be empty: `pgrep firecracker`, `ip -br link | grep zstap`, `ls /zerostress/data/supervisor/runs`, `losetup -a`. SELinux denials are in `/var/log/audit/audit.log`.

## System settings
Users `zerostress-sup` (group `kvm`, and the groups of the four slots), `zerostress-web` and `caddy`, group `zerostress-ipc`; `zerostress-vm0` to `zerostress-vm3`, one per slot, as which Firecracker runs (no login, nothing of their own but the run directory the supervisor hands to the slot's group and the slot's tap); `zerostress`, with no sudo and no login, owns the code and runs every build (npm, vite, go run third-party code, so never as root or as an administrator), and `./zs install` and `./zs update` give it back any file someone wrote as root; the logs in `logs/` hold visitors' addresses and are root's only (`0600`); `/dev/kvm` is `0660`; a `zerostress` zone and a `zerostress-egress` policy in firewalld; the nftables table `inet zerostress` appears on the first `zsnet up`. Only `sshd` and Caddy (80, 443) listen outside. The kernel parameter `spec_store_bypass_disable=seccomp` forces the Speculative Store Bypass mitigation on every seccomp process, including each Firecracker (`/proc/<pid>/status` shows `thread force mitigated`).
