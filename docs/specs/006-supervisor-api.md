# 006. API супервизора и очередь

Статус: реализовано на Go. **Версия 1** (одноразовые задачи, очередь, API, восстановление) и **версия 2** (сессии, команды в уже запущенный браузер, подтверждения человека, разделы 3.7 и 3.8) реализованы и проверены сквозными тестами на сервере (47 и 106 проверок), плюс выдача артефактов (`GET /v1/runs/{id}/artifacts/{name}`, 005, 3.6). Ограничения проверки: раздел 8.

> Пути на сервере в этой спеке даны в раскладке до 7 ноября 2026 (`/opt/zerostress/...`, `/etc/zerostress`, `/var/lib/zerostress*`). Сейчас всё лежит в каталоге проекта `/zerostress` (`bin/`, `images/`, `config/`, `data/`, `run/`), см. [010](010-layout-and-deploy.md), 4.0.

## 1. Цель и границы
Описать службу-супервизор: что она принимает от веб-слоя, как ставит задачи в очередь, где хранит состояние и результаты, как выглядит её API и как она ведёт себя при сбоях. Жизненный цикл одной микро-ВМ описан в [002](002-microvm-lifecycle.md), сеть в [003](003-guest-network.md), образ и агент гостя в [004](004-guest-image.md), сборщик улик, схема улик и протокол команд в [005](005-collector.md), веб-слой и привратник в 007.

Супервизор не ходит в интернет, не вызывает модель, не читает недоверенный контент: он запускает микро-ВМ, передаёт в неё задачу и сохраняет то, что вернулось.

## 2. Решение
- Одна служба `zerostress-supervisor` на Go, только стандартная библиотека (правило привилегированного компонента из CLAUDE.md). Один статический бинарник, рантайма на хосте нет. Сборка и проверки: [supervisor/build.sh](../../supervisor/build.sh) (`go vet`, тесты с `-race`).
- Один процесс, одна очередь в памяти, состояние и результаты на диске. Брокер сообщений не нужен (см. [BACKLOG](../backlog.md), «Решения по очереди»).
- API: HTTP/1.1 по Unix-сокету `/run/zerostress/supervisor.sock` (владелец `zerostress-sup`, группа `zerostress-ipc`, права `0660`). Доступ дают права файловой системы: подключиться может только веб-слой. Токены владельцев задач, лимиты по IP и код доступа проверяет веб-слой (007); супервизор независимо проверяет форму запроса и свои лимиты.
- Хранилище: SQLite через встроенный `node:sqlite` (файл `/var/lib/zerostress/supervisor.db`) для состояний и принятых запросов (ссылка хранится до конца срока хранения, 3.6; нужна, чтобы очередь пережила перезапуск), файлы NDJSON для улик (`/var/lib/zerostress/results/<run_id>.ndjson`, права `0600`). Каталог запуска (диск, сокеты) уничтожается после задачи, результаты хранятся отдельно.
- Внешние процессы вызываются без оболочки (`spawn` с массивом аргументов): `sudo /opt/zerostress/bin/zsnet up|down N` и `sudo /opt/zerostress/bin/zsvm run|stop|recover`. Firecracker запускает не супервизор, а root-помощник `zsvm` как юнит systemd с фиксированными лимитами (3.3).

## 3. Как работает

### 3.1 Состояния и причины отказа
Состояния те же, что в 002: `queued → preparing → booting → running → destroying → done | failed`. Переход в `destroying` обязателен из любого состояния. Для сессий (3.7, версия 2) добавляется состояние `session` между `running` и `destroying`: проход `scan` закончен, ВМ жива и ждёт команды.

Причина (`reason`) задана для `failed`:
| Причина | Когда |
|---|---|
| `queue_timeout` | задача ждала в очереди дольше `SUP_QUEUE_WAIT_S` |
| `cancelled` | запрос `DELETE` |
| `net_setup` | `zsnet up` вернул ошибку |
| `disk_copy` | не удалось создать диск (в том числе мало места) |
| `fc_api` | Firecracker ответил не 204 на шаг настройки |
| `fc_crashed` | процесс Firecracker завершился сам до конца задачи |
| `boot_timeout` | агент не принял соединение за `SUP_BOOT_TIMEOUT_S` |
| `timeout` | агент вернул статус `timeout` или сработал жёсткий потолок |
| `oversize` | агент вернул статус `oversize` |
| `collector_failed` | статус агента `exited_nonzero` или `start_failed` |
| `agent_error` | статусы агента `busy`, `bad_job`, рукопожатие vsock не удалось |
| `supervisor_restart` | супервизор перезапущен во время задачи (см. 3.5) |
| `internal` | любое непредвиденное исключение |

Результат при `done`: статус агента `ok`. При `failed` с причинами `timeout`, `oversize`, `collector_failed` частично собранные улики сохраняются и помечаются неполными (`partial: true`).

### 3.2 Очередь
- Порядок FIFO. Одновременно выполняется не больше `SUP_CONCURRENCY` задач (слотов 0–3 в `zsnet`; значение по умолчанию 2 до замера, см. раздел 9).
- В очереди не больше `SUP_QUEUE_MAX` задач (по умолчанию 20); сверх этого `POST` получает `429` и `Retry-After`.
- Позиция в очереди возвращается в состоянии `queued` и обновляется событиями.
- Слот выдаёт пул: освобождение слота обязательно в блоке `finally` независимо от результата.

### 3.3 Один запуск (сводка, детали в 002)
1. Выделить слот N, создать каталог `/var/lib/zerostress/runs/<run_id>/` (`0700`).
2. Копия диска: `cp --sparse=always` образа `guest-rootfs.ext4`, права `0600`.
3. `sudo zsnet up N`.
4. Запустить `sudo zsvm run N <run_id> <MEM_MIB> <VCPU>` ([deploy/helpers/zsvm](../../deploy/helpers/zsvm)). Помощник проверяет аргументы (слот 0–3, `run_id` по шаблону UUID, память 256–4096, vCPU 1–4, каталог запуска существует, не символьная ссылка и принадлежит `zerostress-sup`) и через `systemd-run --pipe --wait` стартует юнит `zsvm-<run_id>.service`: Firecracker от `zerostress-sup` с лимитами в cgroup (`MemoryMax` = память ВМ + 640 МиБ, без swap, `CPUQuota` = vCPU × 100%, `TasksMax=128`, запись на диск 200 МБ/с на весь диск), защитой юнита (`NoNewPrivileges`, `ProtectSystem=strict` с записью только в каталог запуска, `PrivateTmp`, `RestrictAddressFamilies=AF_UNIX`, `DevicePolicy=closed` с доступом только к `/dev/kvm` и `/dev/net/tun`, и другие) и `ExecStopPost=+zsnet down N`. Команда `zsvm run` не возвращается, пока юнит жив: её завершение означает, что ВМ нет. Серийная консоль гостя приходит в её stdout и читается супервизором в кольцевой буфер 64 КиБ (неограниченная запись в файл заполнила бы диск).
5. Настроить по REST: `machine-config`, `boot-source`, `drives/rootfs`, `network-interfaces/net1`, `vsock`, затем `actions` (`InstanceStart`).
6. Опрашивать vsock (`CONNECT 5000` через `<каталог>/v.sock`) до первого рукопожатия `OK` или до `SUP_BOOT_TIMEOUT_S`.
7. Передать задачу (одна строка JSON), читать поток NDJSON, каждую строку сразу писать в файл результата и рассылать подписчикам SSE; последняя строка с `"type":"status"` завершает задачу.
8. Уничтожить: `sudo zsvm stop <run_id>` (юнит получает `SIGTERM`; `ExecStopPost` убирает сеть слота), дождаться завершения `zsvm run` (слот нельзя отдавать раньше: запоздавший `zsnet down` снёс бы сеть следующей ВМ на этом слоте), `sudo zsnet down N` (повтор, идемпотентно), удалить каталог запуска, вернуть слот. Если супервизор умер, юнит продолжает жить, и при старте `zsvm recover` останавливает все оставшиеся `zsvm-*.service`.

Лимит времени сборщика (60 с) задан в самом образе, в юните агента (004), и супервизором не меняется. Жёсткий потолок жизни (`SUP_HARD_TIMEOUT_S`, по умолчанию 90 с) считается от начала `preparing`: по его истечении принудительно выполняется шаг 8.

### 3.4 Что супервизор не доверяет
- Строки улик от агента проходят как данные: супервизор не разбирает их содержимое, кроме трёх случаев: подсчёт размера, строка статуса и (только для сессий, версия 2) две управляющие строки `session_ready` и `cmd_result` (3.7, 3.8). Управляющая строка признаётся, только если она короче 4 КиБ, имеет `type:"evidence"` и ожидаемую форму; ответ `cmd_result` засчитывается только команде, которая сейчас в полёте, и только с логическим `ok`. Всё остальное, в том числе подделка таких строк страницей или сборщиком, остаётся обычной уликой. Финальный статус определяется только по последней строке потока (подделанная сборщиком строка `status` в середине потока ничего не меняет, см. 004, раздел 8c). Улики публикуются сразу по приходу; задерживается только короткая строка, похожая на статус, пока следующая строка не покажет, последняя ли она.
- Поле `url` не подставляется ни в одну команду, путь или журнал целиком (в журнал идут `run_id`, схема, длина и имя хоста; ссылка может содержать личные токены).
- `run_id` генерируется самим супервизором (`crypto.randomUUID`) и проверяется регулярным выражением перед любым использованием в путях. Номер слота — целое 0–3.

### 3.5 Восстановление при старте
Выполняется до приёма запросов:
1. Найти процессы `firecracker`, в командной строке которых (`/proc/<pid>/cmdline`) есть путь каталога запусков, и убить их.
2. `sudo zsnet down N` для всех слотов (идемпотентно).
3. Удалить все каталоги в `/var/lib/zerostress/runs/` и loop-монтирования, если есть.
4. Задачи в БД в состояниях `preparing`, `booting`, `running`, `destroying` перевести в `failed` с причиной `supervisor_restart` (микро-ВМ уже уничтожены на шагах 1–3, повторять их автоматически нельзя: у ссылки могут быть побочные эффекты).
5. Задачи в состоянии `queued` остаются в очереди в прежнем порядке (запрос хранится в БД) и запускаются, как только освободятся слоты; время ожидания продолжает считаться от `created_at`.

### 3.6 Срок хранения
Результаты и записи в БД удаляются через `SUP_RESULT_TTL_H` (по умолчанию 24 часа), задание очистки раз в 10 минут. Срок записывается в каждую задачу.

### 3.7 Сессии (версия 2)
Запрос с полем `session` означает: после прохода `scan` (005, 3.1) ВМ не уничтожается, а остаётся жить и принимает команды. Без `session` ничего не меняется: одноразовая задача с потолком `SUP_HARD_TIMEOUT_S`.

- **Состояния.** `running` (идёт проход `scan`) → `session` (ВМ жива, ждёт команды или исполняет их) → `destroying`. Исполнение команды состояние не меняет, оно видно в событиях `command` (3.8). Переход в `session` сопровождается событием `session_ready` от сборщика (005).
- **Простой** (`idle_s`, по умолчанию `SUP_SESSION_IDLE_S`, не более 120 с): время без команд после `session_ready` или после последнего `cmd_result`. Ожидание подтверждения (3.8) таймер простоя не считает, но общее время `max_s` продолжает идти. **Простой считает супервизор, не сборщик:** только он знает, что человек решает о рискованной команде. В гостя уходит одно `session.max_s`; по истечении простоя супервизор сам отправляет обычную команду `close` (в событиях `command` она помечена `"by":"supervisor"`, `command_id` `idle-close`). Таймер стоит, пока есть команда в очереди, в полёте или в ожидании подтверждения, и запускается заново после каждого `cmd_result`, отказа, истечения срока подтверждения.
- **Общее время** (`max_s`, по умолчанию `SUP_SESSION_MAX_S`, не более 600 с): от начала `running`.
- **Нормальное закрытие:** команда `close`, истечение простоя или `max_s`: сборщик завершается кодом 0, задача `done` (005, раздел 6).
- **Жёсткий потолок сессии**, который держит супервизор независимо от сборщика: `SUP_BOOT_TIMEOUT_S + max_s + SUP_SESSION_GRACE_S` от начала `preparing`. По истечении принудительное уничтожение, причина `timeout`, улики сохраняются как неполные.
- **Слоты.** Сессия занимает слот на всё время жизни. Чтобы сессии не отнимали пропускную способность у остальных, одновременно допускается не более `SUP_SESSION_SLOTS` сессий (по умолчанию 1 из `K=2`). Пока лимит исчерпан, задача с `session` ждёт в очереди, а задачи без сессии идут мимо неё (FIFO с пропуском); `queue_timeout` общий.
- **Перезапуск супервизора.** Сессия не переживает его: `failed`, `supervisor_restart`; ожидающие подтверждения команды аннулируются (событие `command` со статусом `voided`).

### 3.8 Команды и подтверждения (версия 2)
Протокол команд описан в [005](005-collector.md), 3.2–3.3. Супервизор остаётся детерминированным привратником: он не разбирает улики и не знает, какие `ref` есть на странице; всё, что он проверяет, зависит только от самой команды.

**Приём** (`POST /v1/runs/{run_id}/commands`, тело — команда по 005). Супервизор:
1. Проверяет состояние: только `session`, иначе `409`.
2. Проверяет форму: известный `cmd` из таблицы 005 (имена из прототипа вроде `constructor` отклоняются), `id` по шаблону `^[A-Za-z0-9_-]{1,64}$`, только допустимые поля с диапазонами (`dy` от −5000 до 5000, `ms` от 0 до 5000, `snap` целое от 0, `ref` и `form` вида `e<число>` или `f<число>e<число>` для элемента внутри `iframe`, в `values` не более 20 полей, ключи вида `ref`, строки до 100 символов без управляющих символов), общий размер канонической записи до 4 КиБ. Иначе `400`. Повторный `id` в запуске: `409`, код `duplicate_id`.
3. Считает лимит: не более `SUP_COMMAND_MAX` команд на запуск (по умолчанию 190: агент пересылает не больше 200 строк за задачу, одна остаётся супервизору на собственный `close`), иначе `429`.
4. Вычисляет `command_sha256`: SHA-256 от канонической записи команды (ключи объектов отсортированы рекурсивно, без пробелов, строки как в JSON, числа только целые, UTF-8). **В гостя уходит именно эта каноническая запись**, поэтому подтверждённый хеш и отправленные байты совпадают по построению. `command_id` в ответах равен `id`, который прислал клиент.
5. **Безопасная** команда (`snapshot`, `scroll`, `wait`, `screenshot`, `open_link`, `back`, `close`) ставится в очередь исполнения запуска. **Рискованная** (`download`, `submit_form`) в гостя не уходит и получает статус `awaiting_approval`.
Ответ `202`: `{"command_id":"…","status":"accepted|awaiting_approval","command_sha256":"…"}`.

**Исполнение.** Команды одного запуска исполняются строго по очереди, по одной: следующая отправляется после `cmd_result` предыдущей. Если `cmd_result` не пришёл за `SUP_COMMAND_TIMEOUT_S` (по умолчанию 30 с), сборщик считается зависшим: ВМ уничтожается, причина `timeout`. Подтверждённая рискованная команда встаёт в **конец** очереди исполнения на момент подтверждения, а не на место приёма.

**Подтверждение** (`POST /v1/runs/{run_id}/approvals`, тело `{"command_id":"…","command_sha256":"…"}`). Принимается, только если команда существует, находится в `awaiting_approval`, хеш совпадает с вычисленным при приёме, не истёк `SUP_APPROVAL_TTL_S` (по умолчанию 300 с от приёма) и сессия жива. Подтверждение одноразовое. Ответы: `202` принято; `409` не в ожидании, повторное или хеш не совпал (`hash_mismatch`); `410` срок истёк (команда получает статус `expired`); `404` нет такой команды.

**Отклонение** (`DELETE /v1/runs/{run_id}/commands/{command_id}`): ожидающая подтверждения или ещё не отправленная команда получает статус `rejected`; уже отправленную отменить нельзя (`409`).

**Статусы команды:** `accepted`, `awaiting_approval`, `approved`, `sent`, `done`, `error` (сборщик ответил `ok:false`), `rejected`, `expired`, `voided` (сессия кончилась раньше), `timeout`. Каждое изменение статуса сохраняется событием `command`: `{"command_id","cmd","status","risk","command_sha256"}`; при приёме событие содержит и саму команду (она пришла от нашего веб-слоя, а не от страницы).

**Что гарантируется.** В гостя попадают только команды из фиксированного набора с проверенными параметрами; рискованная команда не уходит без подтверждения, привязанного к хешу её точного содержимого, поэтому подменить содержимое после подтверждения или использовать подтверждение дважды нельзя. Подтверждение выдаёт только веб-слой после решения человека (доступ к сокету даёт право файла, 007); модель до сокета не дотягивается и подтвердить сама не может (CLAUDE.md, правило 8). В журнале службы остаются `run_id`, `command_id`, тип, статус и `command_sha256`, но не `values` и не ссылка.

**Зависимость от агента (версия 2 протокола, 004).** Супервизор шлёт команды в том же vsock-соединении после строки задачи; агент пересылает их в stdin сборщика, проверяя только «JSON-объект до 4 КиБ, не более 200 строк», и по-прежнему считает EOF клиента уходом клиента. Агент и сборщик проверяют форму команд повторно (двойная проверка). Агент v2 реализован и проверен тестами агента ([004](004-guest-image.md), раздел 8e); статус `bad_command` агента супервизор относит к причине `agent_error`.

## 4. Что запускает
| Что | Пользователь | Примечание |
|---|---|---|
| `/opt/zerostress/supervisor/zerostress-supervisor` | `zerostress-sup` | служба systemd `zerostress-supervisor.service` |
| `firecracker` на задачу | `zerostress-sup` | юнит `zsvm-<run_id>.service`, группа `kvm`, лимиты cgroup, `NoNewPrivileges` |
| `sudo /opt/zerostress/bin/zsnet up\|down N` | `root` через sudoers | только эти две команды (001, 003) |
| `sudo /opt/zerostress/bin/zsvm run\|stop\|recover` | `root` через sudoers | правило `/etc/sudoers.d/zerostress-vm`, аргументы проверяются ещё раз внутри помощника |

Решение по открытому вопросу 1 из 001: оставляем `sudo zsnet` и не даём супервизору `CAP_NET_ADMIN`. Следствие: `NoNewPrivileges=yes` для этой службы включить нельзя (проверено: `sudo` отказывается работать с этим флагом). Набор параметров юнита, **проверенный на сервере** (4 ноября 2026, SELinux `Enforcing`, см. раздел 8):

```
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectKernelTunables=yes
ProtectControlGroups=yes
LockPersonality=yes
RestrictAddressFamilies=AF_UNIX AF_NETLINK
ReadWritePaths=/var/lib/zerostress /run/zerostress
```

`AF_NETLINK` обязателен: без него `zsnet` не открывает netlink-сокет (`ip`, `nft`). `AF_INET` не нужен. Для `ProtectKernelTunables=yes` `zsnet` не пишет в sysctl: он только проверяет, что `net.ipv4.ip_forward=1` (значение задано постоянно в `/etc/sysctl.d`).

**Если параметры окажутся несовместимыми** (например, после смены образа Firecracker или политики SELinux), варианты по возрастанию изменений: (1) убрать мешающий параметр по результатам `deploy/test/unit-compat.sh`; (2) вынести `zsnet` в отдельную маленькую службу под `root`, слушающую Unix-сокет и принимающую только `up N` и `down N`: тогда у супервизора можно включить `NoNewPrivileges=yes` и убрать `sudo`; (3) дать супервизору `AmbientCapabilities=CAP_NET_ADMIN` вместо `sudo` (самый широкий вариант: компрометация супервизора даёт полный контроль над сетью хоста, поэтому не рекомендуется).

Настройки только из окружения (файл `config/supervisor.env`, права `0640 root:zerostress-sup`), секретов в нём нет:

## 5. Интерфейсы

HTTP по Unix-сокету, тела запросов и ответов JSON (`Content-Type: application/json`), максимальный размер тела запроса 64 КиБ. Все пути с префиксом `/v1`. Неизвестные поля в запросе отклоняются.

### `POST /v1/runs`
Запрос: `{"kind":"url","url":"https://example.com/path"}`; для сессии (версия 2) добавляется необязательное `"session":{"idle_s":60,"max_s":300}` (`idle_s` от 5 до 120, `max_s` от 30 до 600, оба необязательны, значения по умолчанию из раздела 4).
Проверки: `kind` равен `url`; `url` строка до 2048 символов, схема `http` или `https`, разбирается встроенным `URL`. Проверка внутренних адресов (SSRF) и разрешение имён остаются за привратником веб-слоя (007); сетевой фильтр хоста (003) защищает независимо.
Ответ `202`: `{"run_id":"<uuid>","state":"queued","position":3}`; для запроса с `session` добавляется `"session":true`.
Ошибки: `400` (форма запроса), `413` (тело больше лимита), `429` (очередь полна, заголовок `Retry-After`), `503` (мало места на диске, супервизор останавливается или сессии выключены: `SUP_SESSION_SLOTS=0`).
Вложения (`kind: "file"`) в первую версию не входят (см. BACKLOG, P1).

### `GET /v1/runs/{run_id}`
Ответ `200`:
```json
{"run_id":"…","state":"running","reason":null,"position":null,
 "created_at":"…","started_at":"…","finished_at":null,
 "agent_status":null,"partial":false,"events":42,"expires_at":"…"}
```
`404`, если записи нет или срок хранения истёк.

### `GET /v1/runs/{run_id}/events`
Поток SSE (`text/event-stream`). Каждое сообщение: `id: <порядковый номер>`, `event: state | evidence | status | command | artifact`, `data: <JSON>`. Состояния приходят как `state`, строки NDJSON из гостя как `evidence`, финальная строка агента как `status`, изменения статуса команд (версия 2, 3.8) как `command`, файлы, забранные у гостя, как `artifact` (005, 3.6: `name`, `bytes`, `sha256`, `mime`, `saved`, при отказе `error`; значения измерены на хосте, а не взяты из слов сборщика). Событие `artifact` приходит раньше терминального состояния. Для завершённых задач сообщения воспроизводятся из файла; `Last-Event-ID` позволяет продолжить. Каждые 15 секунд отправляется комментарий `:keepalive`. Отключение клиента не отменяет задачу.

### `GET /v1/runs/{run_id}/artifacts/{name}`
Файл, который супервизор забрал у гостя (005, 3.6). `name` только в виде `<16 hex>.png|bin`, иначе `404`. Ответ `200` с `Content-Type: image/png` для `.png` и `application/octet-stream` для `.bin` (тип выбирает хост по расширению, а не страница), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cache-Control: no-store`. `404`, если запуска или файла нет; `405` для любого метода, кроме `GET`. Файлы лежат в `/var/lib/zerostress/artifacts/<run_id>/` (права `0700`) и удаляются вместе с результатами. Содержимое остаётся данными враждебной страницы: PNG не разбирается супервизором.

### `DELETE /v1/runs/{run_id}`
Отмена: из очереди убирает, у выполняющейся запускает уничтожение с причиной `cancelled`. Ответ `202` или `409`, если задача уже в терминальном состоянии.

### Команды и подтверждения (версия 2)
Ответы с ошибкой содержат `{"error":"…","code":"…"}`; `code` один из `not_found`, `bad_command`, `not_session`, `duplicate_id`, `limit`, `not_waiting`, `hash_mismatch`, `expired`, `too_late`. Тело подтверждения принимает ровно два поля; любое другое или неверный тип даёт `400`.
- `POST /v1/runs/{run_id}/commands` — принять команду (3.8). `202` с `command_id`, `status`, `command_sha256`; `400` форма; `404` нет запуска; `409` не в состоянии `session` (в том числе пока сессия не сообщила готовность) или повторный `id`; `429` лимит команд.
- `POST /v1/runs/{run_id}/approvals` — подтвердить рискованную команду по `command_id` и `command_sha256`. `202` с `{"command_id","status":"approved"}`; `400` форма; `404`; `409` (не в ожидании, повтор, `hash_mismatch`, сессия не принимает); `410` срок истёк.
- `DELETE /v1/runs/{run_id}/commands/{command_id}` — отклонить ожидающую или не отправленную команду. `202` с `{"command_id","status":"rejected"}`; `404`; `409` уже отправлена или завершена.
В представлении `GET /v1/runs/{run_id}` для сессий добавляется `"session":{"idle_s":…,"max_s":…}` и `"commands":{"total":…,"awaiting_approval":…}`; состояние может быть `session`.

### `GET /v1/health`
`{"ok":true,"version":"…","concurrency":2,"running":1,"queued":0,"free_gb":94,"image_sha256":"…"}`; в версии 2 добавляется `"sessions":{"running":0,"limit":1}`. `image_sha256` читается из `manifest.json` установленного образа (004).

## 6. Ограничения и поведение при ошибках
| Ситуация | Поведение |
|---|---|
| Любое исключение при выполнении задачи | блок `finally`: уничтожение (3.3, шаг 8), слот возвращается, причина `internal` или более точная |
| Падение Firecracker | `failed`, `fc_crashed`, улики, пришедшие до обрыва, сохранены |
| Клиент SSE отключился | задача продолжается |
| Остановка службы (`SIGTERM`) | перестать принимать `POST` (`503`), дать выполняющимся задачам завершиться не дольше 10 с, остальные уничтожить (`failed`, `supervisor_restart`); задачи в очереди остаются в БД и продолжатся после запуска (3.5) |
| Мало места на диске | `POST` получает `503`, уже принятые задачи выполняются |
| Файл результата вырос выше `1 МиБ` плюс статус | не бывает: лимит держит агент (004); супервизор дополнительно обрывает чтение на `2 МиБ` и убивает микро-ВМ |
| Команда без `cmd_result` дольше `SUP_COMMAND_TIMEOUT_S` (версия 2) | сборщик считается зависшим: уничтожение, `failed`, `timeout`, улики сохранены как неполные |
| Команда или подтверждение пришли не в состоянии `session` (версия 2) | `409`, ничего не отправляется в гостя |
| Веб-слой ничего не шлёт в сессии (версия 2) | простой `idle_s` закрывает сессию (`done`); ожидающие команды получают `voided` |
| Сессия закрылась, пока команда ждала подтверждения (версия 2) | статус `voided`, подтверждение после этого получает `409` |

### Сравнение TypeScript и Go (4 ноября 2026)
Обе реализации поддерживают весь контракт, включая сессии и подтверждения, работали как одна и та же служба `zerostress-supervisor` и **проходят одни и те же сквозные тесты на настоящих микро-ВМ без единого изменения в тестах**: [supervisor-e2e.sh](../../deploy/test/supervisor-e2e.sh) (47 из 47) и [supervisor-sessions-e2e.sh](../../deploy/test/supervisor-sessions-e2e.sh) (106 из 106). Обе были только на стандартной библиотеке. Осталась Go-версия, [supervisor/](../../supervisor/); TypeScript-версия удалена, её код в истории git.

Замер (скрипт замера удалён вместе с TypeScript-версией): один сервер (2 vCPU, 8 ГБ), один образ, 12 коротких задач на двух слотах.
| | TypeScript | Go |
|---|---|---|
| установлено на хост | 85 КБ исходников и **Node 201 МБ** | **7,8 МБ**, статический бинарник, рантайма нет |
| старт до первого ответа API | 0,36 с | 0,18 с |
| память в покое / после 12 задач | 104 / 174 МБ | 11 / 17 МБ |
| процессорное время супервизора на 12 задач | 11,5 с | 9,2 с |
| время 12 задач (стена) | 40,3 с | 40,0 с |
| исходники без пустых строк и комментариев | 1883 строки, 13 файлов | 3097 строк, 13 файлов |
| тесты | 115 тестов, 1963 строки | 172 тест-функции, 5273 строки, плюс 158 случаев сверки с TypeScript |
| хранилище | SQLite из `node:sqlite` (в Node помечен экспериментальным, в юните `--disable-warning=ExperimentalWarning`) | файлы JSON и NDJSON |
| сборка | нет (Node стирает типы), `tsc --noEmit` для проверки | 14 с на проверки, тесты с `-race` и сборку |

**Что видно из цифр.** Время задач одинаково: оно определяется микро-ВМ и процессором хоста, а не языком супервизора. Различается то, что супервизор держит на привилегированном хосте: Go в десять раз меньше памяти, вдвое быстрее старт, а главное, **нет рантайма Node (201 МБ кода) на хосте с `sudo` к `zsnet` и `zsvm`**. Почему процессорное время супервизора около 0,8 с на задачу в обеих реализациях, не выяснено (общая причина, возможно разбор консоли ВМ и опрос готовности агента); разница в 20% на 12 задачах не показательна.

**Что показала сама работа над Go (не только цифры):**
- Перенос тестов нашёл ошибку и в эталоне: после обрыва записи (авария посреди добавления строки) последняя строка журнала событий оставалась неполной, и чтение событий запуска в TypeScript бросало исключение навсегда, а следующее событие склеивалось с обрывком. Исправлено в обеих реализациях, с тестами (`supervisor/test/store.test.ts`, `store_test.go`).
- В Go нашлась гонка в `execute` (причина `agent_error` вместо `fc_crashed`, если ВМ умерла вместе с обрывом потока), проверка идентификатора в `Store.Delete`, расхождения в причине отмены. В TypeScript гонок такого рода нет по построению (один поток), в Go их ловит детектор гонок и тесты, но следить за блокировками приходится самому.
- **Единственное, что подменённый хост показать не мог, показал сквозной тест на сервере:** `systemd-run --pipe` внутри `zsvm` не принимает от Go обычные трубы для `stdout`/`stderr` («Failed to start transient service unit: Connection reset by peer»), а Node даёт дочерним процессам пары Unix-сокетов и потому работал. В Go-версии для этого сделан `stdioSocket()`. Урок: любая новая реализация обязана пройти сквозной тест на настоящей ВМ, модульных тестов недостаточно.
- Подмена хоста не покрывает `launchFirecracker` в Go (порядок шести запросов настройки проверяет только сквозной тест).
- Единственное известное расхождение формы: одиночный суррогат в JSON (`"\ud800"`) TypeScript сохраняет в канонической записи как есть, Go заменяет на U+FFFD; хеш при этом остаётся согласованным с тем, что уходит в гостя. Для запросов нашего веб-слоя недостижимо.

**Оговорки.** Go писался вторым, по готовому дизайну и тестам TypeScript, поэтому время написания и число найденных ошибок напрямую не сравнимы. Замер на 12 задачах и двух слотах; под большей нагрузкой и с настоящим сборщиком не проверялось. `jailer` не используется ни там, ни там.

**Решение: Go.** Рекомендация принята для привилегированного супервизора. Причины по существу: нет рантайма Node с `sudo`-доступом на хосте, на порядок меньше памяти, статический бинарник одним файлом, нет экспериментального `node:sqlite`, типизированная конкурентность с детектором гонок. Против: исходники в 1,6 раза длиннее, остальной проект (веб-слой, сборщик) на TypeScript, то есть два языка в репозитории; блокировками нужно управлять самому. Принято с этой ценой: два языка в репозитории (Go для привилегированного хоста, TypeScript для остального).

Супервизор v2: [commands.go](../../supervisor/commands.go) (таблица команд, проверка, каноническая запись, хеш), [session.go](../../supervisor/session.go) (команды, подтверждения, часы сессии), состояние `session`, слоты сессий, потолок сессии, маршруты `commands`, `approvals`, отклонение, миграция базы (колонки лимитов сессии). **Проверено модульными тестами на подменённом хосте и по HTTP (110 тестов всего, 77 новых):**
- **Команды:** все девять типов, риск по типу, отклонение неизвестных типов (включая имена из прототипа), лишних и недостающих полей, чисел вне диапазона и нецелых, форм `ref`, значений `values` (число, длина, управляющие символы), записи больше 4 КиБ; каноническая запись не зависит от порядка ключей, любое изменение любого поля меняет хеш.
- **Подтверждения:** рискованная команда не уходит в гостя без подтверждения; неверный, чужой, пустой хеш (в том числе в верхнем регистре) подтверждения не даёт и команду не снимает с ожидания; подтверждение одноразовое; истёкшее даёт `410`, в том числе когда таймер ещё не сработал; подтверждённая команда идёт в конец очереди; отклонённая не отправляется.
- **Исполнение:** по одной команде, по порядку; ответ засчитывается только команде в полёте и только с логическим `ok`; код ошибки гостя передаётся дальше только как короткий токен из строчных букв, цифр и `_`; нет ответа за `SUP_COMMAND_TIMEOUT_S` даёт `timeout`; ошибка записи в гостя даёт `agent_error`; после `close` ничего не отправляется, даже если на сам `close` уже ответили.
- **Время:** простой закрывает сессию командой супервизора, не считается при ожидании подтверждения и запускается заново после него; потолок сессии срабатывает при сборщике, игнорирующем `close`; одноразовый потолок на сессию не действует.
- **Слоты сессий:** вторая сессия ждёт, обычные задачи проходят мимо неё, после освобождения она стартует; при `SUP_SESSION_SLOTS=0` запрос с `session` получает `503`.
- **Перезапуск и остановка:** сессия при старте получает `supervisor_restart`, открытые команды помечаются `voided`; поставленная в очередь сессия переживает перезапуск вместе с лимитами; при остановке службы открытые команды аннулируются.
- **Подделка:** `session_ready` и `cmd_result` неверной формы, с чужим `id`, длиннее 4 КиБ, внутри текста страницы или в одноразовой задаче ничего не меняют.
- **Контроль самих тестов:** набор мутаций (каждая правка защиты по отдельности: проверка хеша, порядок очереди, проверка типа и формы управляющих строк, потолок, `end()`, слоты, коды ответов и другие); все пойманы, кроме двух эквивалентных (лишняя очистка таймера и ранняя проверка шаблона `id` при отклонении, итог тот же). Найденные при этом дыры закрыты тестами (команды за `close`, ответ с неверным типом `ok`, потолок сессии против одноразового).
- Тесты прошли шесть раз подряд и три копии одновременно; одна гонка в тесте (фиксированная пауза вместо ожидания) была найдена и исправлена.

**Решения, принятые при реализации (отличаются от черновика):** (1) простой считает супервизор, а не сборщик (3.7); (2) улики публикуются сразу, задерживается только строка, похожая на статус (3.4); (3) `SUP_COMMAND_MAX` по умолчанию 190, а не 200; (4) `ref` допускает префикс `f<число>` для `iframe`; (5) повторный `id` даёт `409`, а не `400`.

**Проверено на сервере с настоящими микро-ВМ** ([supervisor-sessions-e2e.sh](../../deploy/test/supervisor-sessions-e2e.sh), 106 проверок; заглушка сборщика говорит на протоколе сессии из 005; супервизор v2 установлен поверх **настоящей старой базы**, миграция колонок прошла; старый [supervisor-e2e.sh](../../deploy/test/supervisor-e2e.sh) после этого проходит 47 из 47):
- Запись команд в настоящее соединение vsock из `FirecrackerVm` (до этого проверялась только на подменённом хосте): команды доходят по порядку и в канонической записи, байт в байт; ответы гостя возвращаются; код ошибки гостя (`ref_not_found`) приходит в событие команды.
- Улики видны, пока сессия жива (`session_ready` в потоке до конца запуска).
- Некорректные команды (семь видов), повторный `id`: `400`/`409`, в гостя не попадает ни одного нового эха.
- Рискованная команда: удерживается, неверный хеш, хеш другой команды, нет поля, неизвестная команда: отказ, и в госте по-прежнему пусто; верный хеш: команда приходит ровно один раз, в точном виде; повторное подтверждение `409`; отклонённая не подтверждается.
- Простой: `idle_s=5` закрывает сессию за 4–15 с командой супервизора (`idle-close`, `by: supervisor`); при ожидании человека за 9 секунд сессия не закрывается, позднее подтверждение работает, потом простой закрывает.
- Команда без ответа: `timeout` через около 30 с, следующая за ней команда `voided`.
- Слоты: вторая сессия ждёт в очереди, обычная задача проходит мимо, после закрытия первой вторая стартует; `health` показывает `queued:1` и `sessions.running:1`.
- Отмена сессии с ожидающей командой: `cancelled`, команда `voided`. `SIGKILL` Firecracker в сессии: `fc_crashed`. `SIGKILL` супервизора в сессии: `supervisor_restart`, ожидающая команда `voided` в журнале событий.
- После каждого сценария хост чист (нет Firecracker, `zstap`, каталогов запуска, юнитов `zsvm-*`); в журнале службы нет ссылок с параметрами и введённого в форму значения, но есть строки о командах (контроль).
- Контроли самого теста: счётчик эха видит эхо и ноль; проверка чистоты хоста замечает намеренно оставленный интерфейс. Первый прогон старого теста упал из-за разбора `health` (появилось второе поле `running`); это ошибка теста, исправлена.

**Версия 2 не проверена:** работа с настоящим сборщиком (его нет, есть заглушка); подтверждение с истёкшим сроком на настоящих ВМ (срок 300 с; проверено модульными тестами и по HTTP); пропускная способность с сессиями; перенос на Go (проверяется на том же сквозном тесте).

## 9. Открытые вопросы
0. **Версия 2 решения, которые могут измениться при реализации:** жёсткое правило «одна команда за раз» (проще и безопаснее, но замедляет длинные сессии), подтверждённая команда в конец очереди, число слотов под сессии (по умолчанию 1 из 2), `idle_s` 60 с (хватит ли веб-слою и модели на размышление).
1. **Скриншот и другие большие улики.** Агент ограничивает поток 1 МиБ (004), а PNG контрольной точки может быть больше. Решение зависит от 005: сжатие, отдельный запрос к агенту или отдельный файл. **Для сессий это острее:** лимит агента 1 МиБ действует на весь поток сессии, а каждый снимок страницы до 64 КиБ (005, 3.4); после примерно пятнадцати снимков агент закончит задачу статусом `oversize`. Нужно либо отдельный (больший) предел потока для сессий в агенте, либо вынос снимков в артефакты. Решается вместе с 005, пока не затрагивает заглушку.
2. ~~Значение `SUP_CONCURRENCY`~~ — измерено, остаётся 2 (project.md, «Параллельность с настоящим Chromium»); пересмотреть, когда появится настоящий сборщик с интерактивными шагами (больше CPU на задачу) или хост побольше.
3. **Токены владельцев и личность подтверждающего.** Живут в веб-слое (007); супервизор хранит только хеш подтверждённой команды и время подтверждения; нужно ли ему хранить признак владельца задачи или идентификатор человека для аудита, решается в 007.
4. **Приоритеты и справедливость очереди** (например, один IP не занимает все слоты): сейчас FIFO, лимиты по IP в 007.
5. **Файлы-вложения** (`kind: "file"`): формат запроса и доставка файла в гостя.
6. **`jailer` и seccomp** для боевого режима (см. 002).
