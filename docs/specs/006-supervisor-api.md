# 006. API супервизора и очередь

Статус: черновик.

## 1. Цель и границы
Описать службу-супервизор: что она принимает от веб-слоя, как ставит задачи в очередь, где хранит состояние и результаты, как выглядит её API и как она ведёт себя при сбоях. Жизненный цикл одной микро-ВМ описан в [002](002-microvm-lifecycle.md), сеть в [003](003-guest-network.md), образ и агент гостя в [004](004-guest-image.md), сборщик улик и схема улик в 005, веб-слой и привратник в 007.

Супервизор не ходит в интернет, не вызывает модель, не читает недоверенный контент: он запускает микро-ВМ, передаёт в неё задачу и сохраняет то, что вернулось.

## 2. Решение
- Одна служба `zerostress-supervisor` на Node.js 24, только стандартная библиотека (правило привилегированного компонента из CLAUDE.md). Типы стираются при запуске (`node` без сборки), проверка типов `tsc --noEmit` выполняется на машине разработки и на сервер не ставится.
- Один процесс, одна очередь в памяти, состояние и результаты на диске. Брокер сообщений не нужен (см. [BACKLOG](../BACKLOG.md), «Решения по очереди»).
- API: HTTP/1.1 по Unix-сокету `/run/zerostress/supervisor.sock` (владелец `zerostress-sup`, группа `zerostress-ipc`, права `0660`). Доступ дают права файловой системы: подключиться может только веб-слой. Токены владельцев задач, лимиты по IP и код доступа проверяет веб-слой (007); супервизор независимо проверяет форму запроса и свои лимиты.
- Хранилище: SQLite через встроенный `node:sqlite` (файл `/var/lib/zerostress/supervisor.db`) для состояний и принятых запросов (ссылка хранится до конца срока хранения, 3.6; нужна, чтобы очередь пережила перезапуск), файлы NDJSON для улик (`/var/lib/zerostress/results/<run_id>.ndjson`, права `0600`). Каталог запуска (диск, сокеты) уничтожается после задачи, результаты хранятся отдельно.
- Внешние процессы вызываются без оболочки (`spawn` с массивом аргументов): `sudo /opt/zerostress/bin/zsnet up|down N` и `sudo /opt/zerostress/bin/zsvm run|stop|recover`. Firecracker запускает не супервизор, а root-помощник `zsvm` как юнит systemd с фиксированными лимитами (3.3).

## 3. Как работает

### 3.1 Состояния и причины отказа
Состояния те же, что в 002: `queued → preparing → booting → running → destroying → done | failed`. Переход в `destroying` обязателен из любого состояния.

Причина (`reason`) задана для `failed`:
| Причина | Когда |
|---|---|
| `queue_timeout` | задача ждала в очереди дольше `SUP_QUEUE_WAIT_S` |
| `cancelled` | запрос `DELETE` |
| `net_setup` | `zsnet up` вернул ошибку |
| `disk_copy` | не удалось создать диск (в том числе мало места) |
| `fc_api` | Firecracker ответил не 204 на шаг настройки |
| `fc_crashed` | процесс Firecracker завершился сам до конца задачи |
| `boot_timeout` | агент не принял соединение за `SUP_BOOT_TIMEOUT_S` |
| `timeout` | агент вернул статус `timeout` или сработал жёсткий потолок |
| `oversize` | агент вернул статус `oversize` |
| `collector_failed` | статус агента `exited_nonzero` или `start_failed` |
| `agent_error` | статусы агента `busy`, `bad_job`, рукопожатие vsock не удалось |
| `supervisor_restart` | супервизор перезапущен во время задачи (см. 3.5) |
| `internal` | любое непредвиденное исключение |

Результат при `done`: статус агента `ok`. При `failed` с причинами `timeout`, `oversize`, `collector_failed` частично собранные улики сохраняются и помечаются неполными (`partial: true`).

### 3.2 Очередь
- Порядок FIFO. Одновременно выполняется не больше `SUP_CONCURRENCY` задач (слотов 0–3 в `zsnet`; значение по умолчанию 2 до замера, см. раздел 9).
- В очереди не больше `SUP_QUEUE_MAX` задач (по умолчанию 20); сверх этого `POST` получает `429` и `Retry-After`.
- Позиция в очереди возвращается в состоянии `queued` и обновляется событиями.
- Слот выдаёт пул: освобождение слота обязательно в блоке `finally` независимо от результата.

### 3.3 Один запуск (сводка, детали в 002)
1. Выделить слот N, создать каталог `/var/lib/zerostress/runs/<run_id>/` (`0700`).
2. Копия диска: `cp --sparse=always` образа `guest-rootfs.ext4`, права `0600`.
3. `sudo zsnet up N`.
4. Запустить `sudo zsvm run N <run_id> <MEM_MIB> <VCPU>` ([deploy/zsvm](../../deploy/zsvm)). Помощник проверяет аргументы (слот 0–3, `run_id` по шаблону UUID, память 256–4096, vCPU 1–4, каталог запуска существует, не символьная ссылка и принадлежит `zerostress-sup`) и через `systemd-run --pipe --wait` стартует юнит `zsvm-<run_id>.service`: Firecracker от `zerostress-sup` с лимитами в cgroup (`MemoryMax` = память ВМ + 640 МиБ, без swap, `CPUQuota` = vCPU × 100%, `TasksMax=128`, запись на диск 200 МБ/с на весь диск), защитой юнита (`NoNewPrivileges`, `ProtectSystem=strict` с записью только в каталог запуска, `PrivateTmp`, `RestrictAddressFamilies=AF_UNIX`, `DevicePolicy=closed` с доступом только к `/dev/kvm` и `/dev/net/tun`, и другие) и `ExecStopPost=+zsnet down N`. Команда `zsvm run` не возвращается, пока юнит жив: её завершение означает, что ВМ нет. Серийная консоль гостя приходит в её stdout и читается супервизором в кольцевой буфер 64 КиБ (неограниченная запись в файл заполнила бы диск).
5. Настроить по REST: `machine-config`, `boot-source`, `drives/rootfs`, `network-interfaces/net1`, `vsock`, затем `actions` (`InstanceStart`).
6. Опрашивать vsock (`CONNECT 5000` через `<каталог>/v.sock`) до первого рукопожатия `OK` или до `SUP_BOOT_TIMEOUT_S`.
7. Передать задачу (одна строка JSON), читать поток NDJSON, каждую строку сразу писать в файл результата и рассылать подписчикам SSE; последняя строка с `"type":"status"` завершает задачу.
8. Уничтожить: `sudo zsvm stop <run_id>` (юнит получает `SIGTERM`; `ExecStopPost` убирает сеть слота), дождаться завершения `zsvm run` (слот нельзя отдавать раньше: запоздавший `zsnet down` снёс бы сеть следующей ВМ на этом слоте), `sudo zsnet down N` (повтор, идемпотентно), удалить каталог запуска, вернуть слот. Если супервизор умер, юнит продолжает жить, и при старте `zsvm recover` останавливает все оставшиеся `zsvm-*.service`.

Лимит времени сборщика (60 с) задан в самом образе, в юните агента (004), и супервизором не меняется. Жёсткий потолок жизни (`SUP_HARD_TIMEOUT_S`, по умолчанию 90 с) считается от начала `preparing`: по его истечении принудительно выполняется шаг 8.

### 3.4 Что супервизор не доверяет
- Строки улик от агента проходят как данные: супервизор не разбирает их содержимое, кроме последней строки статуса и подсчёта размера. Финальный статус определяется только по последней строке потока (подделанная сборщиком строка `status` в середине потока ничего не меняет, см. 004, раздел 8c).
- Поле `url` не подставляется ни в одну команду, путь или журнал целиком (в журнал идут `run_id`, схема, длина и имя хоста; ссылка может содержать личные токены).
- `run_id` генерируется самим супервизором (`crypto.randomUUID`) и проверяется регулярным выражением перед любым использованием в путях. Номер слота — целое 0–3.

### 3.5 Восстановление при старте
Выполняется до приёма запросов:
1. Найти процессы `firecracker`, в командной строке которых (`/proc/<pid>/cmdline`) есть путь каталога запусков, и убить их.
2. `sudo zsnet down N` для всех слотов (идемпотентно).
3. Удалить все каталоги в `/var/lib/zerostress/runs/` и loop-монтирования, если есть.
4. Задачи в БД в состояниях `preparing`, `booting`, `running`, `destroying` перевести в `failed` с причиной `supervisor_restart` (микро-ВМ уже уничтожены на шагах 1–3, повторять их автоматически нельзя: у ссылки могут быть побочные эффекты).
5. Задачи в состоянии `queued` остаются в очереди в прежнем порядке (запрос хранится в БД) и запускаются, как только освободятся слоты; время ожидания продолжает считаться от `created_at`.

### 3.6 Срок хранения
Результаты и записи в БД удаляются через `SUP_RESULT_TTL_H` (по умолчанию 24 часа), задание очистки раз в 10 минут. Срок записывается в каждую задачу.

## 4. Что запускает
| Что | Пользователь | Примечание |
|---|---|---|
| `node supervisor/src/main.ts` | `zerostress-sup` | служба systemd `zerostress-supervisor.service` |
| `firecracker` на задачу | `zerostress-sup` | юнит `zsvm-<run_id>.service`, группа `kvm`, лимиты cgroup, `NoNewPrivileges` |
| `sudo /opt/zerostress/bin/zsnet up\|down N` | `root` через sudoers | только эти две команды (001, 003) |
| `sudo /opt/zerostress/bin/zsvm run\|stop\|recover` | `root` через sudoers | правило `/etc/sudoers.d/zerostress-vm`, аргументы проверяются ещё раз внутри помощника |

Решение по открытому вопросу 1 из 001: оставляем `sudo zsnet` и не даём супервизору `CAP_NET_ADMIN`. Следствие: `NoNewPrivileges=yes` для этой службы включить нельзя (проверено: `sudo` отказывается работать с этим флагом). Набор параметров юнита, **проверенный на сервере** (4 ноября 2026, SELinux `Enforcing`, см. раздел 8):

```
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectKernelTunables=yes
ProtectControlGroups=yes
LockPersonality=yes
RestrictAddressFamilies=AF_UNIX AF_NETLINK
ReadWritePaths=/var/lib/zerostress /run/zerostress
```

`AF_NETLINK` обязателен: без него `zsnet` не открывает netlink-сокет (`ip`, `nft`). `AF_INET` не нужен. Для `ProtectKernelTunables=yes` `zsnet` не пишет в sysctl: он только проверяет, что `net.ipv4.ip_forward=1` (значение задано постоянно в `/etc/sysctl.d`).

**Если параметры окажутся несовместимыми** (например, после смены образа Firecracker или политики SELinux), варианты по возрастанию изменений: (1) убрать мешающий параметр по результатам `deploy/test/unit-compat.sh`; (2) вынести `zsnet` в отдельную маленькую службу под `root`, слушающую Unix-сокет и принимающую только `up N` и `down N`: тогда у супервизора можно включить `NoNewPrivileges=yes` и убрать `sudo`; (3) дать супервизору `AmbientCapabilities=CAP_NET_ADMIN` вместо `sudo` (самый широкий вариант: компрометация супервизора даёт полный контроль над сетью хоста, поэтому не рекомендуется).

Настройки только из окружения (файл `/etc/zerostress/supervisor.env`, права `0640 root:zerostress-sup`), секретов в нём нет:
| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SUP_CONCURRENCY` | 2 | число одновременных микро-ВМ (0–4) |
| `SUP_QUEUE_MAX` | 20 | длина очереди |
| `SUP_QUEUE_WAIT_S` | 120 | сколько задача ждёт слот |
| `SUP_BOOT_TIMEOUT_S` | 15 | готовность агента |
| `SUP_HARD_TIMEOUT_S` | 90 | потолок жизни микро-ВМ |
| `SUP_VCPU`, `SUP_MEM_MIB` | 2, 1024 | ресурсы микро-ВМ |
| `SUP_MIN_FREE_GB` | 20 | порог свободного места для приёма задач |
| `SUP_RESULT_TTL_H` | 24 | срок хранения результатов |

## 5. Интерфейсы

HTTP по Unix-сокету, тела запросов и ответов JSON (`Content-Type: application/json`), максимальный размер тела запроса 64 КиБ. Все пути с префиксом `/v1`. Неизвестные поля в запросе отклоняются.

### `POST /v1/runs`
Запрос: `{"kind":"url","url":"https://example.com/path"}`.
Проверки: `kind` равен `url`; `url` строка до 2048 символов, схема `http` или `https`, разбирается встроенным `URL`. Проверка внутренних адресов (SSRF) и разрешение имён остаются за привратником веб-слоя (007); сетевой фильтр хоста (003) защищает независимо.
Ответ `202`: `{"run_id":"<uuid>","state":"queued","position":3}`.
Ошибки: `400` (форма запроса), `413` (тело больше лимита), `429` (очередь полна, заголовок `Retry-After`), `503` (мало места на диске или супервизор останавливается).
Вложения (`kind: "file"`) в первую версию не входят (см. BACKLOG, P1).

### `GET /v1/runs/{run_id}`
Ответ `200`:
```json
{"run_id":"…","state":"running","reason":null,"position":null,
 "created_at":"…","started_at":"…","finished_at":null,
 "agent_status":null,"partial":false,"events":42,"expires_at":"…"}
```
`404`, если записи нет или срок хранения истёк.

### `GET /v1/runs/{run_id}/events`
Поток SSE (`text/event-stream`). Каждое сообщение: `id: <порядковый номер>`, `event: state | evidence | status`, `data: <JSON>`. Состояния приходят как `state`, строки NDJSON из гостя как `evidence`, финальная строка агента как `status`. Для завершённых задач сообщения воспроизводятся из файла; `Last-Event-ID` позволяет продолжить. Каждые 15 секунд отправляется комментарий `:keepalive`. Отключение клиента не отменяет задачу.

### `DELETE /v1/runs/{run_id}`
Отмена: из очереди убирает, у выполняющейся запускает уничтожение с причиной `cancelled`. Ответ `202` или `409`, если задача уже в терминальном состоянии.

### `GET /v1/health`
`{"ok":true,"version":"…","concurrency":2,"running":1,"queued":0,"free_gb":94,"image_sha256":"…"}`. `image_sha256` читается из `manifest.json` установленного образа (004).

## 6. Ограничения и поведение при ошибках
| Ситуация | Поведение |
|---|---|
| Любое исключение при выполнении задачи | блок `finally`: уничтожение (3.3, шаг 8), слот возвращается, причина `internal` или более точная |
| Падение Firecracker | `failed`, `fc_crashed`, улики, пришедшие до обрыва, сохранены |
| Клиент SSE отключился | задача продолжается |
| Остановка службы (`SIGTERM`) | перестать принимать `POST` (`503`), дать выполняющимся задачам завершиться не дольше 10 с, остальные уничтожить (`failed`, `supervisor_restart`); задачи в очереди остаются в БД и продолжатся после запуска (3.5) |
| Мало места на диске | `POST` получает `503`, уже принятые задачи выполняются |
| Файл результата вырос выше `1 МиБ` плюс статус | не бывает: лимит держит агент (004); супервизор дополнительно обрывает чтение на `2 МиБ` и убивает микро-ВМ |

## 7. Проверка
| Проверка | Ожидание |
|---|---|
| Модульные тесты автомата и пула слотов с подменой Firecracker и `zsnet` | слот освобождается при любом исходе, из любого состояния есть путь в `destroying` |
| Задача с заглушкой сборщика (`hello`) через API | `done`, события через SSE, после неё нет Firecracker, `zstap*`, каталога запуска |
| Падение Firecracker во время задачи (`kill -9`) | `fc_crashed`, ресурсы убраны |
| `DELETE` выполняющейся задачи | `cancelled`, ресурсы убраны |
| Принудительное завершение супервизора посреди задачи и старт | остатки найдены и убраны, задача `failed/supervisor_restart` |
| 25 запросов подряд при `SUP_QUEUE_MAX=20` | первые приняты, остальные получают `429` |
| Двадцать задач подряд | нет утечек (интерфейсов, правил `nft`, каталогов, процессов, дескрипторов) |
| Подделка статуса сборщиком | итоговый статус определяет последняя строка |
| Некорректный запрос (схема `file:`, длинный `url`, лишние поля, не JSON) | `400` |
| Права сокета | пользователь вне `zerostress-ipc` подключиться не может |

## 8. Что проверено и что нет

Что нашёл сквозной тест (исправлено):
- Проба готовности агента (соединение без задачи) занимала флаг `busy`, и пришедшая сразу за ней задача получала `busy`. Исправлено в агенте: флаг занимается после чтения задачи (004, раздел 8c).
- systemd по умолчанию (`KillMode=control-group`) шлёт SIGTERM всей группе, и микро-ВМ гибли раньше, чем супервизор успевал их остановить. В юните `KillMode=mixed`; при остановке причина фиксируется как `supervisor_restart`, а не `fc_crashed`.

**Язык реализации не зафиксирован.** Контракт (этот документ, интерфейс бэкенда, `zsnet`, протокол агента, сквозной тест) от языка не зависит, поэтому реализации сравнимы на одном приёмочном тесте. Эталон: TypeScript. Следующий кандидат: Go (статический бинарник, без Node на хосте, `context` и группы процессов в стандартной библиотеке; хранилище на файлах вместо SQLite). Rust и Python возможны после готового продукта. Метрики сравнения: зависимости и размер на хосте, память, время старта, число строк, трудоёмкость, прохождение сквозного теста.

## 9. Открытые вопросы
1. **Скриншот и другие большие улики.** Агент ограничивает поток 1 МиБ (004), а PNG контрольной точки может быть больше. Решение зависит от 005: сжатие, отдельный запрос к агенту или отдельный файл.
2. **Значение `SUP_CONCURRENCY`.** Определяется замером 1–4 микро-ВМ с настоящим Chromium (память, CPU, время навигации).
3. **Токены владельцев и подтверждение действий.** Живут в веб-слое (007); нужно ли супервизору хранить признак владельца задачи, решается там.
4. **Приоритеты и справедливость очереди** (например, один IP не занимает все слоты): сейчас FIFO, лимиты по IP в 007.
5. **Файлы-вложения** (`kind: "file"`): формат запроса и доставка файла в гостя.
6. **`jailer` и seccomp** для боевого режима (см. 002).
