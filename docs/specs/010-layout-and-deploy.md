# 010. Структура проекта, конфигурация и развёртывание

Статус: **согласовано 6 ноября 2026, пересмотрено 7 ноября 2026** (решение «всё в одном каталоге», 4.0). Репозиторий переложен в ветке `feature/layout`; сервер переехал в `/zerostress` 7 ноября 2026 (`deploy/migrate-from-opt.sh`, раздел 7).

## 1. Цель и границы
Человек и агент должны находить любой файл без поиска, переносить сервис на новую машину одной командой и не путать код, настройки окружения и сгенерированные файлы. Спецификация задаёт раскладку репозитория, раскладку на сервере, место каждого конфига и порядок установки. Как работает каждый компонент, описано в 001–009, 011, 012.

## 2. Принципы (заданы владельцем проекта 6 ноября 2026)
1. **Предсказуемость.** Если разработчик тратит время на поиск файла, структура проиграла.
2. **Изоляция слоёв.** Код не смешивается с конфигурацией окружения и со сгенерированными файлами.
3. **Единообразие имён.** Только нижний регистр, без пробелов, слова через дефис (kebab-case).
4. **«Всё ношу с собой» (7 ноября 2026).** Один каталог проекта, в нём лежит всё и от него всё работает, как у хостинговых панелей; удобство владельца и разработки важнее соглашений Linux о раскладке.

## 3. На что опирались (проверено 6 ноября 2026)
- **FHS 3.0** (Linux Foundation, 19 марта 2015), по `hier(7)` из `man-pages-6.06` на Rocky 10 (сайт стандарта закрыт от автоматического чтения): `/opt` «add-on packages that contain static files»; `/etc/opt` и `/var/opt` для настроек и данных пакетов из `/opt`; `/var/lib` «variable state information»; `/var/cache` «data cached for programs».
- **systemd** `file-hierarchy(7)` и `systemd.exec(5)` (systemd 257): `/opt` не упоминается; `StateDirectory=` создаёт каталог в `/var/lib/`, `CacheDirectory=` в `/var/cache/`, `RuntimeDirectory=` в `/run/`, `ConfigurationDirectory=` в `/etc/`; `/var/cache` можно очистить без вреда, кроме времени на пересоздание.
- **The Twelve-Factor App** (Adam Wiggins, 12factor.net, обновлено в 2017): настройки в переменных окружения, проверка «код можно открыть, не раскрыв ключей»; строгое разделение build, release, run, выпуск неизменяем, у него уникальный идентификатор, откат к прошлому выпуску; логи в stdout, хранением занимается среда.

- **Один каталог у других продуктов** (по их документации, 7 ноября 2026): mailcow ставится `git clone` в `/opt/mailcow-dockerized`, конфиг `mailcow.conf` лежит там же, обновление `./update.sh`; Coolify держит исходники, `.env`, ключи, бэкапы и прокси под `/data/coolify`; aaPanel ставится в `/www`.

## 4. Решения

### 4.0 Всё в одном каталоге `/zerostress` (7 ноября 2026; заменяет раскладку сервера из 4.3, 4.5 и 4.8 версии от 6 ноября)
Каталог проекта — это рабочая копия git, на сервере `/zerostress`. Рядом с кодом лежат места, которые заполняют установщик и службы (все в `.gitignore`):

| Каталог | Что | Владелец | Тип SELinux |
|---|---|---|---|
| код (`supervisor/`, `web/`, `guest/`, `deploy/`, `docs/`) | git | владелец рабочей копии | `usr_t` |
| `config/` | `web.env`, `supervisor.env` (правит человек), `Caddyfile` (делает установщик), образцы `*.example` в git | root, файлы `0640 root:<служба>` | `etc_t` |
| `bin/` | `firecracker`, `zsvm`, `zsnet`, `caddy`, `zerostress-supervisor` | root, никто другой не может менять (`zsvm` и `zsnet` идут от root через sudo) | `bin_t` |
| `runtime/` | `node/`, `go/` | root | `bin_t` для `*/bin` |
| `images/` | образ гостя | root | `usr_t` |
| `data/` | `supervisor/` (запуски ВМ, итоги, база), `web/` (отчёты), `geo/`, `caddy/` (сертификаты) | у каждой службы свой | `var_lib_t` |
| `logs/` | `web.log`, `supervisor.log`, `caddy.log` (службы пишут через `StandardOutput=append:`; ротация `logrotate`) | root | `var_log_t` |
| `run/` | `supervisor.sock` | `zerostress-sup:zerostress-ipc` | `var_lib_t` |
| `build/` | всё, что делают сборки | владелец рабочей копии и root (образ) | `usr_t` |

Служба сайта работает прямо из рабочей копии (`web/`, только чтение для неё) и отдаёт `build/client`; копии кода больше нет. Супервизор и помощники работают из `bin/` (копии root, потому что `zsvm` исполняется от root). Вне каталога остаётся только то, что система читает лишь из своих мест: юниты (`/etc/systemd/system`), правила sudo, sysctl, udev, logrotate, метки SELinux и зона firewalld. Их ставит `./zs install` из `deploy/files/`, руками они не правятся.

Одна команда `./zs`: `install [этап…]`, `update` (git pull, сборка, перезапуск), `start|stop|restart|status`, `logs`, `config web|supervisor` (правка и перезапуск), `verify [--live]`, `dev`. Веб-слой берёт пути по умолчанию от своего расположения (`web/server/../..`), поэтому у разработчика тот же код работает в его рабочей копии без настроек; `./zs dev` поднимает сайт на порту 8081 со своими данными в `build/dev`.

**Проверено 7 ноября 2026 (SELinux Enforcing).** Новый каталог в `/` или `/opt` получает тип `default_t` или `usr_t`, и systemd не может создать в нём журнал консоли ВМ (отказ `init_t` → `usr_t`); с правилом `var_lib_t` для `data/` ВМ загружается, тест образа проходит. На отдельном префиксе с тем же набором правил под пользователями и защитой служб (`ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`): Node из `runtime/` читает переменную из `config/`, пишет в `data/web`, пишет журнал в `logs/`; сокет создаётся в `run/`; Firecracker и Caddy из `bin/` запускаются; запись пользователя сайта в `bin/` отклонена (`EROFS`); новых отказов SELinux ноль. `/home` не годится: у служб и ВМ `ProtectHome=yes`. Второй супервизор для проверки не запускался: при старте он вызывает `zsvm recover`, а тот гасит все ВМ хоста.

**Два файла настроек, а не один:** ключ модели должна читать только служба сайта (правило containment 2); с одним файлом его видел бы и супервизор.

### 4.1 Корень репозитория говорит, где исполняется код
| Каталог | Где исполняется | Права |
|---|---|---|
| `supervisor/` | хост | привилегированно (только stdlib Go) |
| `web/` | хост, служба `zerostress-web`; `web/client/` в браузере посетителя | без привилегий |
| `guest/` | внутри микро-ВМ: `agent/` (Go), `collector/` (Playwright), `image/` (сборка образа) | непривилегированный пользователь гостя |
| `deploy/` | при установке на хост | root |
| `docs/` | — | — |
| `build/` | всё сгенерированное, в `.gitignore` целиком | — |

Причина: раньше код гостя лежал в двух местах (`collector/`, `guest-image/`), по имени не было видно, что оба уходят в ВМ. Каталог `probes/` удалён: решения, ради которых писались пробники, приняты и записаны (project.md, 005), сами файлы остались в истории git.

### 4.2 Сгенерированное только в `build/`
Бинарники супервизора и агента гостя, собранный клиент, рабочие файлы сборки образа, снимки браузерной проверки кладутся в `build/` (подкаталоги `supervisor/`, `guest-agent/`, `client/`, `image/`, `e2e/`). `rm -rf build/` ничего не ломает. Раньше они лежали рядом с исходниками (`supervisor/zerostress-supervisor`, `web/client/dist/`, снимки в `web/client/mockups/`, хотя это не макеты).

### 4.3 Настройки и системные файлы
**Настройки служб — переменные окружения** в `config/web.env` и `config/supervisor.env` (формат `ИМЯ=значение`, читает systemd через `EnvironmentFile=`), а не `*.conf`: так требует Twelve-Factor, и расширение честно говорит о формате. Образцы `config/*.env.example` лежат там же и в git; `./zs install host` создаёт настоящие файлы из них один раз и больше не трогает; `./zs verify` сверяет имена (не значения). Каждая переменная описана в [../config.md](../config.md); тесты `web/server/test/env-example.test.ts` и `supervisor/envexample_test.go` падают, если код читает переменную, которой нет в образце или в описании (7 ноября расширенный тест нашёл пять строковых переменных супервизора, пропущенных версией от 6 ноября).

**Системные файлы** лежат в `deploy/files/` по своему пути на хосте (`deploy/files/etc/sudoers.d/zerostress-vm` ставится в `/etc/sudoers.d/zerostress-vm`): юниты, sudoers, sysctl, udev, logrotate. Исходники помощников `zsvm` и `zsnet` — `deploy/helpers/`, шаблон Caddyfile — `deploy/templates/`. Раньше шесть конфигов были вписаны в скрипты (heredoc).

Данные, которые едут вместе с кодом (правила хуков `web/hooks/rules/*.json`, промпт `web/agent/prompts/`), конфигами окружения не считаются: они версионируются с кодом.

### 4.4 Версии в одном месте
`deploy/versions.env`: Node, Firecracker, Caddy, Go, ядро гостя, база Ubuntu, с хешами. Раньше версии были разбросаны по четырём скриптам и CI.

### 4.5 Установка по этапам, одна команда
`./zs install [этап…]`: `host` (пользователи, каталоги проекта с владельцами и типами SELinux, настройки из образцов, `/dev/kvm`, logrotate, параметр ядра `spec_store_bypass_disable=seccomp`), `network` (сеть гостей), `runtime` (Node, Go, Firecracker, Caddy по хешам), `image` (сборка и установка образа гостя), `supervisor`, `web`, `verify`; без этапа — все по порядку. Этапы лежат в `deploy/steps/` (`10-host.sh` … `90-verify.sh`), общие функции в `deploy/lib.sh`. Сборки идут от владельца рабочей копии, не от root. Раньше номера скриптов совпадали с номерами спецификаций (`001`, `002`, `003`, `006`, `010`), Node и Go ставились руками, параметр ядра тоже.

### 4.6 Тесты
- Go: рядом с кодом (`*_test.go`), этого требует сам Go.
- TypeScript и JavaScript: в каталоге `test/` модуля (`web/agent/test/`, `web/client/test/`, `guest/collector/test/`). Раньше клиент держал тесты рядом с кодом, остальной `web/` в `test/`.
- Тесты на настоящих микро-ВМ: только `deploy/test/` (в том числе бывшие `guest-image/test/`).

### 4.7 Имена
Нижний регистр, слова через дефис. Исключения только по требованию инструмента: `README.md`, `LICENSE`, `CLAUDE.md` (их ищут GitHub и Claude Code), `*_test.go` и `*_linux.go` (Go). Переименованы `docs/*.md` (`status.md`, `deploy.md`, …) и страницы клиента (`report.tsx`, …).

### 4.8 Переезд работающего сервера
`deploy/migrate-from-opt.sh` переносит сервер со старой раскладки (`/opt/zerostress`, `/opt/zerostress-src`, `/etc/zerostress`, `/var/lib/zerostress*`, `/etc/caddy`, `/usr/local/bin/caddy`, `/opt/node`, `/opt/go`): `mv /opt/zerostress-src /zerostress`, затем `prepare` (без простоя: каталоги, настройки копией из `/etc/zerostress` без мёртвой `AGENT_MODE`, рантайм, образ, сборки, первая копия данных), `switch` (около минуты простоя: остановка, вторая копия данных, новые юниты и sudoers, запуск, `verify`; при сбое старые юниты возвращаются сами), `rollback`, `cleanup` (удаляет старые места, когда новая раскладка поработала). До `cleanup` ничего старого не удаляется.

## 5. Как работать
| Задача | Что делать |
|---|---|
| Изменить код | рабочая копия → тесты → коммит |
| Выкатить | `./zs update` (git pull, сборка, перезапуск, `verify`) или `sudo ./zs install web` / `supervisor` |
| Изменить ключ или лимиты | `./zs config web` (правка, перезапуск) |
| Логи | `./zs logs [web|supervisor|caddy] [-f]` |
| Новый сервер | `git clone … /zerostress`, `sudo ./zs install host`, `./zs config web`, `sudo ./zs install`, `./zs verify --live`, DNS |
| Локально | `cp config/web.env.example config/web.env` (ключ по желанию), `./zs dev` |

Агент: рабочая копия свободно; установка в бой только с явного разрешения владельца; значения из `config/*.env` не читает и не печатает (только имена).
