# 004. Образ гостя и чистый диск на задачу

Статус: реализовано и проверено на сервере: образ, агент гостя (протокол v1 и сессии v2), выдача артефактов; настоящий сборщик кладётся поверх оверлеем (005).

> Пути на сервере в этой спеке даны в раскладке до 7 ноября 2026 (`/opt/zerostress/...`, `/etc/zerostress`, `/var/lib/zerostress*`). Сейчас всё лежит в каталоге проекта `/zerostress` (`bin/`, `images/`, `config/`, `data/`, `run/`), см. [010](010-layout-and-deploy.md), 4.0.

## 1. Цель и границы
Описать, из чего состоит образ диска микро-ВМ, как он собирается воспроизводимо и как каждая задача получает чистый диск. Жизненный цикл микро-ВМ описан в [002](002-microvm-lifecycle.md), сеть в [003](003-guest-network.md), сам сборщик улик и схема улик в 005.

## 2. Решение
- Один неизменяемый **базовый образ**, собранный скриптом из репозитория, с зафиксированными версиями и контрольной суммой.
- На каждую задачу делается **копия** базового образа, микро-ВМ работает с копией, после задачи копия удаляется. Копия никогда не используется повторно.
- Образ содержит только то, что нужно сборщику: систему, Node, Playwright, Chromium, пользователя без прав. Секретов в образе нет.
- Ядро гостя хранится отдельно от образа диска.

## 3. Состав образа

### 3.1 Что внутри (проверено 3 ноября 2026)
| Компонент | Значение |
|---|---|
| Основа | Ubuntu 24.04 (корневая файловая система из CI Firecracker, содержит systemd и SSH) |
| Node | 24.22.2, официальный архив `nodejs.org`, контрольная сумма проверена по `SHASUMS256.txt`, лежит в `/opt/node` |
| Playwright | 1.65.0, установлен в `/opt/collector/node_modules` |
| Браузеры | Playwright кладёт их в `/opt/pw-browsers`: Chrome Headless Shell 158.0.8127.18, вероятно, также полный Chromium и ffmpeg |
| Пользователь | `pw`, без прав администратора, от него запускаются сборщик и Chromium |
| Размер | видимый 5 ГБ (разрежённый файл), занято на диске 2,0 ГБ; `/opt/node` 208 МБ, `/opt/collector` 19 МБ, `/opt/pw-browsers` 681 МБ |
| Ядро | отдельный файл `vmlinux-6.18.56` из CI Firecracker, в образ не входит |
| Песочница Chromium | работает от `pw` (`max_user_namespaces` 7951), запуск с `chromiumSandbox: true` проверен |

### 3.2 Что должно быть в образе дополнительно (предложение)
- Служба systemd для сборщика или сервис приёма задач (зависит от канала связи, см. раздел 9).
- Корневая файловая система смонтирована только для чтения, а `/tmp`, `/home/pw` и `/var` на `tmpfs` (не проверено, потребует правки инициализации).
- Только необходимые слушающие порты в госте.
- Часы и часовой пояс настроены (см. раздел 9).
- Шрифты для скриншотов страниц на разных языках (см. раздел 9).
- Из образа убраны кэш пакетов, документация и инструменты сборки.

## 4. Как собирается образ (процедура)
Скрипт `guest/image/build.sh` (будет в репозитории) выполняет:
1. Скачать ядро и корневую систему Ubuntu из CI Firecracker (корзина S3 `spec.ccfc.min`). Префикс сборки закрепляется явно (на 3 ноября использовался `firecracker-ci/20261028-84df49062576-0/`, ядро 6.18.56), а не выбирается «последний».
2. Распаковать `squashfs` (`unsquashfs`), сгенерировать ключ для канала SSH (если выбран SSH) и положить публичную часть в `authorized_keys`.
3. Создать файл образа (`truncate -s 5G`), отформатировать (`mkfs.ext4 -d` из распакованного дерева).
4. Смонтировать образ через loop, подключить `/dev`, `/dev/pts`, `/proc`, `/sys`, выполнить `chroot` и установить зависимости: пакеты apt, Node (скачать, сверить контрольную сумму, распаковать), `npm install playwright@1.65.0`, браузеры, создать пользователя `pw`.
5. Размонтировать (всегда, через `trap`), проверить файловую систему (`e2fsck -fn`), посчитать SHA-256 и записать вместе с версиями в файл `manifest`.
6. Положить образ в `/opt/zerostress/images/` (`root:root`, только чтение).

### Ошибки, обнаруженные при первой сборке (учесть в скрипте)
| Проблема | Причина | Решение |
|---|---|---|
| `apt` не может создать временные файлы | у `/tmp` в образе права `755` | `chmod 1777` для `/tmp` и `/var/tmp` до запуска apt |
| `apt` не находит каталог архивов | в образе нет `/var/cache/apt/archives/partial` и каталогов списков | создать `/var/cache/apt/archives/partial`, `/var/lib/apt/lists/partial`, `/var/log/apt` |
| `node` не найден после установки | у `sudo` на Rocky ограниченный `PATH` без `/usr/local/bin` | задать `PATH` внутри `chroot` явно |
| Ошибка `posix_openpt` | в `chroot` не смонтирован `/dev/pts` | смонтировать `devpts` |
| Предупреждения локали | в образе нет настроенной локали | задать `LC_ALL=C` на время сборки (локаль в рабочем режиме настроить отдельно) |

### Воспроизводимость
Версии Node (с проверкой суммы), Playwright и префикс CI закреплены. Пакеты `apt` берутся из архива Ubuntu на момент сборки и не закреплены, это известное отступление. Возможное улучшение: использовать зеркало с фиксированным снимком (не проверено).

## 5. Диск на задачу
1. Супервизор делает `cp --sparse=always <базовый образ> /var/lib/zerostress/runs/<run_id>/rootfs.ext4`; копия принадлежит `zerostress-sup`, права `0600`.
2. Микро-ВМ подключает копию как корневой диск (запись разрешена).
3. После задачи копия удаляется вместе с каталогом запуска.

**Измерено (3 ноября 2026):** копирование образа (2,0 ГБ занято) заняло 0,73 с при холодном кэше и 0,57 с при тёплом. Файловая система хоста ext4, `reflink` не поддерживается. Замер одиночный, при параллельной нагрузке не проверялся.

**Расход диска:** до 2 ГБ на каждую активную задачу (три слота около 6 ГБ). Порог свободного места, ниже которого задачи отклоняются, нужно задать (предлагается не меньше 20 ГБ).

Оптимизации (пул готовых копий, пул загруженных микро-ВМ, снимки Firecracker) вынесены в [BACKLOG](../backlog.md) и в первой версии не делаются.

## 6. Что запускает
Во время сборки: `unsquashfs`, `mkfs.ext4`, `mount`, `chroot`, `apt-get`, `curl`, `sha256sum`, `npm`, `npx playwright install`, `useradd`, `e2fsck`. Выполняется вручную или скриптом от администратора, не службой.

Во время работы микро-ВМ: инициализация systemd гостя, служба канала связи, сборщик, Chromium по запросу.

## 7. Проверка
| Проверка | Ожидание |
|---|---|
| Повторная сборка с теми же версиями | образ запускается, версии в `manifest` совпадают |
| SHA-256 образа | совпадает с `manifest`, меняется только при пересборке |
| Загрузка микро-ВМ из копии | готовность не больше 15 с |
| Chromium от `pw` с включённой песочницей | запускается, страница открывается |
| `ss -tlnp` в госте | слушает только служба канала связи |
| Поиск секретов и ключей в образе | ничего, кроме временного ключа канала (если он есть) |
| Время в госте | совпадает с хостом с точностью до нескольких секунд |
| Скриншот страницы с кириллицей и иероглифами | текст отображён |
| Чистота копии | после задачи копия удалена, файлы предыдущей задачи в новой копии отсутствуют |
| Копирование под нагрузкой (три задачи одновременно) | время копирования остаётся приемлемым |

## 8. Что проверено и что нет
**Проверено:** сборка по процедуре из раздела 4 (с исправлениями из таблицы ошибок); состав и размеры из раздела 3.1; Chromium от `pw` с включённой песочницей; семь сценариев редиректов в госте; время копирования.

**Не проверено:** `manifest` и скрипт сборки (их ещё нет); корневая система только для чтения с `tmpfs`; работа без `sshd` (канал vsock); шрифты; часы гостя; установка только `chrome-headless-shell` без полного Chromium; воспроизводимая пересборка; поддержка vsock в ядре гостя (для этого нужен драйвер virtio-vsock).

## 8a. Проверка vsock (3 ноября 2026)
| Что | Результат |
|---|---|
| Устройство в Firecracker | `PUT /vsock` с `guest_cid` 3 и путём к Unix-сокету на хосте: ответ 204 |
| Ядро гостя 6.18.56 | `CONFIG_VSOCKETS=y`, `CONFIG_VIRTIO_VSOCKETS=y` (встроены, не модули), `/dev/vsock` в госте есть |
| Инструменты в образе | есть `python3` и `socat` |
| Хост → гость (через Unix-сокет Firecracker, команда `CONNECT 5000`) | рукопожатие `OK`, задержка пинга в среднем 0,21 мс (максимум 0,39 мс) |
| Передача данных гость → хост | 50 МиБ за 0,09 с (около 530 МиБ/с) |

Ограничения проверки: приёмник в госте запускался вручную через SSH (автозапуска при загрузке пока нет); направление гость → хост (гость инициирует соединение) не проверялось; использовался `python3`. У Node нет встроенной поддержки сокетов vsock, поэтому для сборщика на Node в госте нужен мост, например `socat VSOCK-LISTEN:порт,fork` к Unix-сокету или к программе сборщика. Работа `socat` с vsock проверена позже (раздел 8b). На стороне хоста Node подключается к обычному Unix-сокету Firecracker без дополнительных пакетов.

## 8b. Приёмник задач в госте: `socat` и агент на Go (3 ноября 2026)
Сравнение двух вариантов приёмника на vsock. Условия: микро-ВМ 2 vCPU и 2048 МиБ, настоящий сборщик на Playwright с Chromium (`chromiumSandbox: true`) от пользователя `pw`, один прогон каждого сценария. Остатки процессов ищутся по полному списку процессов, без фильтра по пользователю. Код эксперимента не сохранён в репозитории.

Агент на Go: слушает vsock-порт, принимает одну строку с задачей (до 64 КиБ), запускает сборщик от `pw` в отдельной группе процессов, стримит его stdout, ограничивает вывод 1 МиБ и время 10 с, при обрыве клиента убивает группу, одновременно держит одну задачу (иначе сразу `busy`), в конце пишет строку статуса (`ok`, `exited_nonzero`, `oversize`, `timeout`, `client_gone`, `busy`, `bad_job`).

| Сценарий | `socat` + обёртка (`timeout`, `head -c`) | Агент на Go |
|---|---|---|
| Задержка заглушки | 530 мс (80 мс с `-t 0.05`) | 30 мс |
| Задача с настоящим Chromium | 940 мс (490 мс с `-t 0.05`) | 440 мс |
| Живая передача событий | первое событие только в конце задачи | через 26 мс |
| Вывод больше лимита | приходит 237–245 КБ, статуса нет | ровно 1 МиБ и статус `oversize` |
| Зависание Chromium | 12,5 с, код 137, остатков нет | 10 с, `timeout`, остатков нет |
| Сборщик убит `SIGKILL` при живом Chromium | остатков нет | остатков нет |
| Обрыв клиента при зависшем Chromium | Chromium (8 процессов) жив ещё около секунды, к 13 с нет | остатков нет через секунду |
| Потомок после обычного `fork` | остаётся | убирается |
| Потомок в отдельной сессии (`setsid`) | остаётся | остаётся |
| Вторая задача при занятом приёмнике | молча ждёт, потом выполняется | сразу `busy` |
| Память приёмника | около 8 МиБ (2 процесса `socat`) | 3,9 МиБ |

Ошибки, найденные в ходе проверки: опция `user=pw` в `socat` для `EXEC` не меняет пользователя (нужна `su=pw`), из-за этого первый прогон шёл от root; проверка остатков с фильтром по пользователю скрывала утечки. Оба недочёта исправлены, цифры выше получены после исправления.

**Решение: агент на Go по vsock.** Контракт сборщика не зависит от приёмника: задача JSON в stdin, события NDJSON в stdout. Приёмник можно заменить без изменения сборщика. Агент на Rust не писали: выигрыш по размеру и памяти оценивается в мегабайты и не оправдывает ещё одну сборку.

Не проверено: нагрузка на память и CPU под Chromium, сложные страницы, потомки в отдельных сессиях (нужны cgroup или отдельное пространство PID, иначе страховка это уничтожение микро-ВМ), автозапуск агента при загрузке, обмен в направлении гость → хост по инициативе гостя, пиновка версий зависимостей агента (`mdlayher/vsock`, `golang.org/x/sys`) и воспроизводимая сборка в образ.

## 8c. Агент в репозитории и дымовой тест образа (4 ноября 2026)
Код: [guest/agent/](../../guest/agent/) (Go 1.27.3, единственная зависимость `golang.org/x/sys`, версия закреплена в `go.sum`), оверлей образа [guest/image/apply-overlay.sh](../../guest/image/apply-overlay.sh) и [guest/image/overlay/](../../guest/image/overlay/), дымовой тест [deploy/test/image-smoke.sh](../../deploy/test/image-smoke.sh) с клиентом хоста на Node без пакетов ([vsock-client.mjs](../../deploy/test/vsock-client.mjs)) и заглушкой сборщика ([stub-collector.mjs](../../deploy/test/stub-collector.mjs)).

**Контракт агента:** клиент шлёт одну строку JSON (до 64 КиБ) и **не закрывает свою сторону на запись** (EOF клиента означает «клиент ушёл» и убивает задачу). Агент стримит stdout сборщика (не более 1 МиБ) и в конце пишет одну строку `{"type":"status",...}` с отдельной строки; затем закрывает соединение. Статусы: `ok`, `exited_nonzero`, `timeout`, `oversize`, `client_gone`, `busy`, `bad_job`, `start_failed`. Принимаются только соединения с CID 2 (хост). Сборщик запускается с чистым окружением, от `pw`, в отдельной группе процессов, которая убивается целиком.

**Проверено (сервер, 2 vCPU, 1 ГиБ, SELinux Enforcing):**
- Тесты агента `go test -race` (3 прогона): все статусы, убийство группы процессов по таймауту и при уходе клиента, `busy`, некорректные задачи, подделка статуса сборщиком, статус на отдельной строке, чистое окружение.
- Дымовой тест образа (оверлей на копию текущего образа, загрузка с vsock и `ip=`): агент готов через 2,4–3,1 с после запуска Firecracker; сборщик работает от `pw`; из гостя доступен публичный интернет (HTTPS по имени), заблокированы `169.254.169.254` и шлюз хоста; вывод ограничен 1 МиБ плюс строка статуса; второй параллельный запрос получает `busy`; в образе нет ключей хоста SSH, `authorized_keys` и `socat`. Копирование образа 0,6–0,7 с.

**Найденные ошибки (исправлены):**
- Закрытие соединения с непрочитанным входом (`busy`, `bad_job`) приводило к RST и потере статуса: агент теперь читает остаток (до 300 мс, до 1 МиБ) перед закрытием.
- Сборщик, пишущий в stdout без учёта обратного давления (`drain`), раздувает память и убивает ВМ с 1 ГиБ по OOM; настоящий сборщик (005) обязан его учитывать.
- Клиент хоста не должен вызывать `process.exit()` после записи в пайп: вывод обрезается по размеру буфера пайпа (64 КиБ).

**Не проверено:** автозапуск после перезагрузки на настоящем сборщике; агент при нескольких виртуальных машинах; воспроизводимая сборка образа (`build.sh`, `manifest`); потомки в отдельной сессии (`setsid`); корневая система только для чтения; часы гостя; скриншот с кириллицей и иероглифами; усиление юнита агента (`NoNewPrivileges` и другое) с настоящим Chromium.

## 8d. Воспроизводимая сборка `build.sh` (4 ноября 2026)
Скрипт [guest/image/build.sh](../../guest/image/build.sh) собирает образ с нуля, запускается от `root` на хосте: `AGENT_BIN=... ./build.sh`. Результат в `$BUILD_DIR/out` (по умолчанию `/var/tmp/zerostress-build/out`): `guest-rootfs.ext4`, ядро и `manifest.json` (хеши, версии, коммит). В `/opt/zerostress/images` ничего не устанавливается автоматически.

Закреплено: префикс CI `firecracker-ci/20261028-84df49062576-0/x86_64` (адрес вида `https://s3.amazonaws.com/spec.ccfc.min/...`, бакет с точками в имени не работает с виртуальным адресом), SHA-256 корневой системы и ядра, Node 24.22.2 (сумма из `SHASUMS256.txt`), Playwright 1.65.0 точной версией и lock-файлом ([guest/collector/](../../guest/collector/)), `npm ci --ignore-scripts`. Ставится только `chromium-headless-shell` (`playwright install --only-shell chromium`), `ffmpeg` и полный Chromium не нужны. Из пакетов `apt` убраны `curl`, `xz-utils` и `xvfb` относительно ручной сборки.

**Проверено (сервер):** сборка с нуля прошла за несколько минут; образ занимает на диске 1,5 ГБ (в ручной сборке 2,0 ГБ); дымовой тест прошёл полностью, включая Chromium с `chromiumSandbox: true` от `pw` (страница с кириллицей, иероглифами и эмодзи отрисована, скриншот снят); агент готов через 2,8 с; копирование образа 0,46 с.

**Закрыто по разделу 7 (4 ноября 2026):**
- Скриншот страницы с кириллицей, иероглифами и эмодзи просмотрен глазами: все три письменности и эмодзи читаемы.
- Часы гостя: расхождение с хостом около 0,5 с (тест допускает до 5 с). Способ синхронизации не настраивался, значение получено после загрузки.
- В госте нет слушающих TCP-сокетов (проверка по `/proc/net/tcp*`); vsock в эту проверку не входит.
- Копирование образа при трёх одновременных запусках с холодным кэшем: по 1,10 с на копию.
- Юнит агента усилен (`NoNewPrivileges`, `ProtectSystem=full`, `ProtectKernelModules`, `ProtectKernelLogs`, `ProtectControlGroups`, `RestrictSUIDSGID`, `LockPersonality`); дымовой тест с настоящим Chromium проходит. `ProtectHome` и `PrivateTmp` не включены, чтобы не ломать `/home/pw` и `/tmp` сборщика.
- Новый образ установлен скриптом [guest/image/install.sh](../../guest/image/install.sh) в `/opt/zerostress/images/guest-rootfs.ext4` вместе с `manifest.json` (скрипт сверяет контрольную сумму образа с манифестом); ручной образ `guest-base.ext4` удалён, как и все файлы ручных экспериментов на сервере (см. [deploy.md](../deploy.md)).

## 8e. Агент v2: сессии и команды (4 ноября 2026)
Протокол (спецификации [005](005-collector.md), [006](006-supervisor-api.md), версия 2) реализован в [guest/agent/](../../guest/agent/): если в задаче есть объект `session`, `stdin` сборщика остаётся открытым, и каждая следующая строка клиента пересылается ему как команда.
- **Проверка формы.** Строка команды: JSON-объект до `MaxCmd` (4096) байт, не более `MaxCmds` (200) команд на задачу. Всё остальное (не JSON, массив, оборванная строка, слишком длинная, слишком много) завершает задачу статусом `bad_command`, сборщик убивается. Пустые строки пропускаются.
- **Один читатель на соединение.** Задача и команды читаются одним буферизованным читателем, иначе читатель задачи «проглатывал» бы команды, присланные вплотную за ней.
- **Лимит времени сессии:** `session.max_s` (по умолчанию 300 с, не больше `-session-max`, 600 с) плюс `-session-grace` (30 с). Задача без `session` ведёт себя как в версии 1: `stdin` закрывается после задачи, лишние строки клиента отбрасываются.
- Неверный тип поля `session` (`true`, строка, массив, `max_s` не число) делает задачу `bad_job`.
- В статусе появилось необязательное поле `commands` (число пересланных команд).
- Флаги юнита по умолчанию заданы: `-session-max 600s -session-grace 30s -max-cmd 4096 -max-cmds 200`.

**Проверено:** тесты агента (`go test -race`, три прогона): команды доходят до сборщика по порядку, пришедшие в одном пакете с задачей не теряются, пустые строки игнорируются, поведение без `session` как в версии 1, неверная форма и все пределы дают `bad_command` и убивают сборщик, таймаут сессии берётся из `max_s` и ограничен агентом, уход клиента убивает сборщик и освобождает агент, сборщик, завершившийся раньше команд, не ошибка, слот занят всё время сессии. Образ пересобран с новым агентом, сквозной тест супервизора версии 1 проходит.
**Найдено тестами и исправлено:** при слишком длинной команде статус `bad_command` доставлялся, но затем приходил `connection reset` (агент закрывал соединение с непрочитанным остатком строки); теперь агент дочитывает остаток (до 300 мс) перед закрытием.
**Проверено на настоящей микро-ВМ по настоящему vsock** ([deploy/test/image-session.sh](../../deploy/test/image-session.sh), заглушка сборщика читает команды, 17 проверок, 4 ноября): команды доходят по порядку и байт в байт; задача и команды одним пакетом не теряются; три вида неверной строки и строка в 5000 байт дают `bad_command`, и статус доходит до клиента (сброса соединения нет), агент после этого свободен; клиент, пропавший посреди сессии, освобождает агент; обычная задача команды не получает. Дымовой тест образа после выноса общего кода в `lib-vm.sh` проходит.
**Найдено этим тестом (правило для сборщика):** агент держит `stdin` открытым, пока сборщик жив, поэтому сборщик обязан завершаться сам после команды `close` (и при `max_s`). Заглушка с открытым `stdin` не завершалась, и агент ждал её до предела клиента. Страховка есть (таймаут сессии `max_s` плюс запас), но завершение по `close` должно быть штатным. Правило записано в [005](005-collector.md).
**В гостевом браузере проверено** (заглушка, простая страница, Chromium с включённой песочницей): `ariaSnapshot({mode:'ai'})` выдаёт `[ref=eN]`, ссылка через `aria-ref=` находится и отдаёт `href`, скрытый (`display:none`) текст в снимок не попадает. Память гостя на простой странице: занято 193 МиБ до запуска браузера и 336 МиБ после снимка и скриншота, браузер около 171 МиБ (PSS). Это не пик на тяжёлых страницах.
**Не проверено:** работа с настоящим сборщиком (005) и с супервизором версии 2 (его ещё нет), пересылка команд, когда сборщик медленный (очередь команд на 16 строк: переполнение даёт `bad_command`; проверено только модульным тестом), таймаут сессии на настоящей ВМ (только модульные тесты; в гостевом прогоне он занял бы больше 30 с запаса), память на тяжёлых страницах.
