# 002. Жизненный цикл микро-ВМ

Статус: черновик.

## 1. Цель и границы
Описать, как супервизор создаёт, запускает, наблюдает и уничтожает одну микро-ВМ на одну задачу. Образ гостя описан в 004, сеть в [003](003-guest-network.md), сборщик улик в 005, внешний интерфейс супервизора в 006.

## 2. Решение
Одна задача получает одну микро-ВМ Firecracker. После задачи (в том числе при ошибке или таймауте) микро-ВМ уничтожается вместе с её диском, сетью и каталогом. Ничего не переиспользуется между задачами.

## 3. Как работает

### 3.1 Состояния
| Состояние | Что происходит | Переход |
|---|---|---|
| `queued` | задача принята, ждёт свободного слота | слот свободен → `preparing` |
| `preparing` | выделяется слот N, создаются каталог и диск, поднимается сеть | готово → `booting`, ошибка → `destroying` |
| `booting` | запущен процесс Firecracker, отправлена конфигурация и `InstanceStart` | гость готов → `running`, таймаут → `destroying` |
| `running` | сборщик в госте выполняет задачу, супервизор ждёт результат | результат получен → `destroying`, таймаут → `destroying` |
| `destroying` | процесс Firecracker останавливается, сеть и каталог убираются | завершено → `done` или `failed` |
| `done` / `failed` | итоговое состояние, результат или причина отказа сохранены | — |

Переход в `destroying` обязателен из любого состояния, в том числе при исключении в самом супервизоре.

### 3.2 Шаги (что делает супервизор)
1. **Принять задачу** и присвоить `run_id`.
2. **Выделить слот N** из пула (0 до K−1). Слот задаёт интерфейс `zstapN`, адреса и MAC (см. 003). Если слотов нет, задача ждёт в очереди.
3. **Подготовить каталог** `/var/lib/zerostress/runs/<run_id>/` (права `0700`).
4. **Подготовить диск гостя.** Способ не выбран (см. раздел 9). Файловая система ext4 не поддерживает мгновенное копирование.
5. **Поднять сеть:** `sudo /opt/zerostress/bin/zsnet up N`.
6. **Запустить Firecracker:** `firecracker --api-sock /var/lib/zerostress/runs/<run_id>/fc.sock --enable-pci`, вывод в журнал запуска. В боевом режиме через `jailer`.
7. **Настроить через API:** `PUT /machine-config` (число vCPU и память), `PUT /boot-source` (ядро и аргументы `console=ttyS0 reboot=k panic=1`), `PUT /drives/rootfs`, `PUT /network-interfaces/net1`, затем `PUT /actions` с `InstanceStart`. Каждый запрос должен вернуть 204.
8. **Дождаться готовности гостя** (таймаут загрузки).
9. **Передать задачу сборщику, получить результат** в виде JSON улик (канал vsock, приёмник — агент на Go, см. [004](004-guest-image.md)).
10. **Уничтожить:** отправить `SIGTERM` процессу Firecracker, через заданное время `SIGKILL`; `sudo zsnet down N`; удалить каталог запуска; вернуть слот в пул.

### 3.3 Лимиты и таймауты (предложение, значения нужно подобрать)
| Параметр | Начальное значение | Основание |
|---|---|---|
| vCPU на микро-ВМ | 2 | проверено |
| Память микро-ВМ | 2048 МиБ | проверено на тесте; при трёх слотах это 6 ГиБ из 7,7 ГиБ, поэтому нужно измерить |
| Параллельных микро-ВМ (K) | 2, возможно 3 | не измерено |
| Таймаут загрузки | 15 с | проверено: готовность около 3,2 с |
| Таймаут задачи | 60 с | не измерено на реальных сайтах |
| Жёсткий потолок жизни микро-ВМ | 90 с | предложение |
| Размер хранимого результата | ограничение на объём JSON и скриншота | не определён |

## 4. Что запускает
| Что | Кто | Права |
|---|---|---|
| Процесс `firecracker` на каждую микро-ВМ | супервизор (`zerostress-sup`) | группа `kvm`, без `root` |
| `zsnet up N` и `zsnet down N` | супервизор через `sudo` | `root`, фиксированные аргументы |
| Процессы гостя: `sshd` (или агент vsock), сборщик, Chromium | внутри микро-ВМ | сборщик и Chromium от пользователя `pw` |

Постоянных дочерних процессов, кроме процессов Firecracker на время задач, нет.

## 5. Интерфейсы
- Вход: запрос от супервизорного API (006): адрес или файл, лимиты.
- Выход: итоговое состояние, JSON улик или причина отказа, журнал запуска.
- Управление Firecracker: REST по Unix-сокету, запросы в разделе 3.2, пункт 7.

## 6. Ограничения и поведение при ошибках
| Ситуация | Поведение |
|---|---|
| API Firecracker вернул не 204 | перейти в `destroying`, состояние `failed`, причина в журнале |
| Гость не стал готов за таймаут загрузки | `destroying`, `failed` |
| Задача превысила таймаут | `destroying`, `failed` с причиной `timeout`, частично собранные улики сохраняются как неполные |
| Падение процесса Firecracker | `destroying`, `failed` |
| Падение или перезапуск супервизора | при старте найти каталоги в `/var/lib/zerostress/runs`, остановить связанные процессы Firecracker (по `run_id` в имени сокета), вызвать `zsnet down` для всех слотов, удалить каталоги |
| Нехватка слотов | задача остаётся в очереди до предела длины очереди, затем отказ |
| Гость пытается занять больше памяти | ограничено конфигурацией микро-ВМ |

Очистка запускается в блоке `finally` и при любом исключении, чтобы не оставлять `tap`, правила и каталоги.

## 7. Проверка
| Проверка | Ожидание |
|---|---|
| Запуск и нормальное завершение | состояние `done`, после завершения нет процесса `firecracker`, `zstapN`, каталога запуска |
| Принудительное завершение супервизора посреди задачи, затем старт | остатки найдены и убраны |
| Зависший гость (цикл в госте) | убит по жёсткому потолку |
| Две и три параллельные задачи | слоты не пересекаются, память хоста в пределах нормы |
| Двадцать задач подряд | нет утечек: интерфейсов, правил nft, каталогов, процессов |

## 8. Что проверено и что нет
**Проверено (3 ноября 2026):**
- Последовательность запросов `machine-config`, `boot-source`, `drives/rootfs`, `network-interfaces/net1`, `actions` давала ответы 204.
- Гость становился доступен по SSH примерно через 3,2 с (верхняя оценка).
- Команда `reboot` в госте корректно завершала Firecracker с кодом 0.
- Очистка в блоке `trap` убирала `tap0` и сокет.
- Микро-ВМ с 2 vCPU и 1–2 ГБ памяти, Chromium внутри работал.
- Память хоста: около +620 МиБ после одного запуска Chromium (грубо).

**Не проверено:** `jailer`, vsock, диск на задачу, параллельность, восстановление после падения супервизора, таймауты на реальных сайтах, реальный выход в интернет.

## 9. Открытые вопросы
1. **Диск на задачу** (ext4 без `reflink`): предложено обычное копирование образа, замер 0,57–0,73 с для 2,0 ГБ (см. [004](004-guest-image.md)); при параллельной нагрузке не проверено.
2. **Канал связи с гостем:** SSH (проверен) или vsock (проверен 3 ноября 2026: драйвер в ядре гостя есть, обмен хост → гость работает, подробности в [004](004-guest-image.md), раздел 8a). Выбран vsock с агентом на Go ([004](004-guest-image.md), раздел 8b). Шаг 9 жизненного цикла: супервизор подключается к Unix-сокету Firecracker, отправляет `CONNECT <порт>`, передаёт задачу и читает NDJSON с финальной строкой статуса.
3. **Предел параллельности K и размер памяти микро-ВМ** по результатам замеров.
4. **`jailer` и фильтры seccomp** для боевого режима: параметры и время запуска.
